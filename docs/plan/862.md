# 862 — Additive `Chunk` / `ChunkedColumn` behind the existing facade

**Issue:** [#862](https://github.com/khurram-uworx/Nivara/issues/862) · **Status:** planned, not started · **Branch:** `khurram/862` (fresh off `main`)

Introduce an internal `Chunk<T>` / `ChunkedColumn<T>` layer around the existing `ColumnStorage<T>` so chunk/block structure exists in the engine, without changing the public `NivaraColumn<T>` / `NivaraFrame` surface and without betting the system on Arrow physics.

Complementary reading: [`ARROW-ROADMAP.md`](ARROW-ROADMAP.md) Phase A, [`ARROW-REVIEW.md`](ARROW-REVIEW.md).

---

## 1. What the issue asks for

- Internal `Chunk<T>` and `ChunkedColumn<T>` around `ColumnStorage<T>`, reusing the zero-copy sharing that already exists.
- Public `NivaraColumn<T>` / `NivaraFrame` behaviour unchanged.
- `Slice` and `Concat` operate chunk-wise, copying only when needed.
- Chunk-aware tests for flat primitive tables.
- Preserve chunk counts through Arrow import/export on an **opt-in** path instead of flattening.
- Record the additive layer in `ARROW-ROADMAP.md` Phase A.

**Non-goals:** variable-binary strings (Phase B), dictionary encoding (#132), zero-copy *import*, any public API break.

| Decision | Outcome |

## 3. Grounded state of the code

**The seam already exists.** `IColumnStorage<T>` (`src/Nivara/Interfaces.cs`) is `internal` and declares exactly: `Length`, `IsVectorizable`, `HasNulls`, `NullMask`, `NullMaskMemory`, `this[int]`, `Slice(int,int)`, `Data`, `TryGetHashCodes`, `AsSpan`, `TryGetSpan`, `AsWritableSpan`.

`NivaraColumn<T>` holds `readonly IColumnStorage<T> storage` and `internal NivaraColumn(IColumnStorage<T>)`. A new storage implementation therefore needs **no change to the column type**.

**`Slice` is already pure delegation.** `NivaraColumn<T>::Slice` validates bounds and calls `storage.Slice(start, length)`, then wraps the result. Chunk-wise slicing falls out of implementing `IColumnStorage<T>.Slice` — no column-file edit required.

**Ten "Unsupported storage type…" throws** are the only hard blockers, in `src/Nivara/NivaraColumn.cs`:

| Line | Message |
|---|---|
| 419 | Unsupported storage type for vectorized operations |
| 617 | Unsupported storage type for vectorized operations |
| 802 | Unsupported storage type for scalar operations |
| 861 | Unsupported storage combination for scalar equality comparison |
| 873 | Unsupported storage type for vectorized operations |
| 953 | Unsupported storage type for scalar operations |
| 1012 | Unsupported storage combination for scalar greater than comparison |
| 1024 | Unsupported storage type for vectorized operations |
| 1104 | Unsupported storage type for scalar operations |
| 1163 | Unsupported storage combination for scalar less than comparison |

Each guards a method that then reads `memoryStorage.Data` and/or `memoryStorage.NullMaskMemory` — both interface members. These are **deletions plus a type substitution**, not a new materialise-fallback layer.

`applyElementwiseBinary` and `applyElementwiseCompare` already fall back to pooled element-wise access through `storage[i]`, so they need nothing beyond a working chunked indexer.

**`ConcatenateColumns`** lives in `ColumnFilterHelper::ConcatenateColumns` and copies everything through reflection into `concatenateColumnsTyped<T>`. Call sites:

- `StreamingWindowProcessor` (two sites)
- `ParallelExecutionHelper`
- `ParallelExecutionStrategy` (two sites)
- `ConcatenationOperation::ConcatenateColumns` (delegates)

The streaming windows loop, which is why concat must stay conservative.

**Arrow facts (Apache.Arrow 23.0.0).**

- `Table.TableFromRecordBatches(Schema, IList<RecordBatch>)` yields one `Column` per field with one array per batch, so every column shares the same chunk grid.
- `Table(Schema, IList<Column>)` and `Column(Field, IList<IArrowArray>)` exist, which is the route that preserves **per-column** chunk counts.
- `ChunkedArray` exposes `ArrayCount`, `Array(i)`, `Length`, `NullCount`.
- `ArrowInterop::ToArrowArray<T>(NivaraSeries<T>)` returns a single `IArrowArray` and structurally cannot express multi-chunk.
- `ArrowInterop::CreateZeroCopyPrimitive<T>` is typed on `NivaraColumn<T>` and already handles slice offsets, so per-chunk zero-copy follows for free.

**Docs gates are unaffected.** `DocSnippetExtractor.IsScanned` excludes `docs/plan/`, so `ARROW-ROADMAP.md` edits bump no `DocsCoveragePins` count, provided no new citation is added to a scanned document.

## 4. Corrections to the plan comment already on the issue

| Claim on the issue | Reality |
|---|---|
| "7 throw sites in `NivaraColumn`" | **10** — see the table in §3 |
| "Emit one Arrow array per chunk" | Not expressible through `TableFromRecordBatches`; that gives every column the same grid. Per-column fidelity needs `new Table(schema, columns)` with each `Column` built from its own array list, and needs a probe |
| "`ChunkedColumn.Dispose` disposes the underlying `ColumnStorage` chunks" | Lifetime bug. Chunks are slices sharing a parent buffer, and `ColumnStorage<T>.Dispose` itself only nulls its lazy tensor view. Disposal must be a no-op of the same shape |
| "Replace the throws with a materialise fallback" | Mostly a deletion — the guard blocks only touch interface members |
| `Chunk<T>` carries `OffsetInColumn` + `FromStorage(storage, offset)` | Redundant. `ColumnStorage<T>.Slice` already carries `dataStart` / `dataLength` |

## 5. Design

```
NivaraColumn<T>            (unchanged, public)
   └─ IColumnStorage<T>    (unchanged, internal)
        ├─ ColumnStorage<T>      flat: T[] + bool[]? mask   [today]
        └─ ChunkedColumn<T>      Chunk<T>[]  (≥2 chunks)    [new]
             └─ Chunk<T>          readonly struct { ColumnStorage<T> Storage; }
```

### `Chunk<T>`
Readonly struct over one already-sliced `ColumnStorage<T>`. Exposes `Length`, `this[int]`, `IsNull(int)`. No offset field.

### `ChunkedColumn<T>`
Implements `IColumnStorage<T>`.

- **Invariant: ≥2 chunks.** A single chunk never produces a `ChunkedColumn<T>`; it collapses to `ColumnStorage<T>`. This is what proves the flat hot path is untouched.
- Cached prefix-offset `int[]` gives O(log n) `this[int]` and cross-boundary null lookup.
- `IsVectorizable` → `ColumnStorageFactory.IsVectorizable<T>()`, so chunked columns route through the existing SIMD path.
- `Data` / `AsSpan` / `NullMask` / `NullMaskMemory` materialise one contiguous copy lazily and cache it. Chunks are never dropped. `internal bool IsMaterialized` exists for tests.
- `NullMask` returns `ReadOnlySpan<bool>.Empty` without allocating when `HasNulls == false`.
- `TryGetSpan` → `false` always; it cannot honour the zero-copy contract.
- `AsWritableSpan` → `NotSupportedException`; writing to a copy is silent data loss.
- `TryGetHashCodes` → `false`; grouping falls back to `EqualityComparer` through `GroupKeyReader<T>`, which already handles the false branch.
- `Slice` walks chunks; a slice landing in one chunk collapses to `ColumnStorage<T>`.
- `Dispose` drops the cached copy and the chunk array, nothing else.

### Consequence to state plainly
Chunking buys **structural fidelity** — slice, concat, and Arrow chunk counts — not compute. Arithmetic on a chunked column pays one cached contiguous copy per operand. Chunk-wise kernels are a follow-up.

## 6. Work breakdown

One commit, one reason.

### Step 0 — probe before touching `src`

Add a `chunked-arrow` mode to `tests/Nivara.SimdProbe`, documented in that project's `README.md`, asserting with the real `Apache.Arrow` reference resolved in-tree:

1. `Table.TableFromRecordBatches(schema, batches)` → `Column(i).Data.ArrayCount == batches.Count`.
2. `new Table(schema, columns)` where two columns have **different** chunk counts → both counts survive, `RowCount` is correct, no validation throw.
3. `new Column(field, IList<IArrowArray>)` round-trips a two-chunk column.
4. `new ChunkedArray(IList<IArrowArray>)` reports `ArrayCount` and `Length` as expected.

This is the gate for the export decision. If (2) fails, fall back to the batched grid and re-raise before writing IO code. An out-of-tree `Add-Type` attempt failed on a `System.Runtime` 8-vs-10 identity mismatch, which is exactly why this belongs in the probe project.

### Step 1 — `feat(storage)`: the chunk layer

`src/Nivara/Storage/Chunk.cs`, `src/Nivara/Storage/ChunkedColumn.cs`

As specified in §5.

`tests/Nivara.Tests/Storage/ChunkedColumnTests.cs`, mirroring `ColumnStorageTests` conventions:

- ≥2-chunk invariant and the one-chunk collapse
- cross-boundary indexer and null mask
- materialisation caching — identity on the second call
- `TryGetSpan == false`
- `AsWritableSpan` throws
- `NullMask` returns empty without allocating when there are no nulls
- disposal leaves chunks usable

### Step 2 — `refactor(column)`: retire the ten guards

`src/Nivara/NivaraColumn.cs`

Delete the blocks listed in §3 and substitute `storage.Data` / `storage.NullMaskMemory`. `AsTensorView` throws `NotSupportedException` for a non-flat backing, naming `.Data`.

Existing `if (storage is ColumnStorage<T> …)` fast paths stay untouched. The element-wise `else` branches need nothing beyond a working indexer.

This commit touches no test expectations — that is the evidence it is behaviour-preserving.

**Pre-check:** audit `src` for `AsWritableSpan` callers on an arbitrary storage before this lands.

### Step 3 — `feat(helpers)`: chunk-preserving concat

`src/Nivara/Helpers/ColumnFilterHelper.cs`

When at least one input storage is `ChunkedColumn<T>`, build the result from the chunk lists with no copy. Otherwise keep today's copy path byte-for-byte.

`ConcatenationOperation::ConcatenateColumns` delegates, so frame-level concat and the parallel strategies inherit the behaviour. The streaming windows and `ParallelExecutionHelper` keep exactly current behaviour because they never feed chunked inputs.

### Step 4 — `feat(io)`: opt-in Arrow chunk preservation

- `ArrowConversionOptions.PreserveChunkStructure`, default `false`, with a remark that it changes chunk counts only, not values.
- **Import:** `ConvertArrowColumnToNivaraColumn` gains a per-array path — one `ColumnStorage<T>` per `ChunkedArray.Array(i)`, assembled into `ChunkedColumn<T>` when `ArrayCount > 1`. Chunk values still copy element-by-element because Arrow buffers are `ReadOnlyMemory<byte>`; what is saved is the flatten pass and the `T?[]` intermediate.
- **Export:** `ToArrowTable` builds one `Column` per frame column from its own per-chunk arrays, via `new Table(schema, columns)`. Zero-copy per chunk reuses `CreateZeroCopyPrimitive<T>` unchanged, including slice offsets.
- **`ToArrowArray<T>`** throws when `PreserveChunkStructure` meets a chunked column, pointing at `ToArrowTable`. Silent flattening is the thing the option exists to prevent.

`tests/Nivara.Tests/IO/ChunkedArrowRoundTripTests.cs`:

- three batches → import → re-export → `ArrayCount == 3` per column
- values and nulls preserved
- default option yields a plain `ColumnStorage<T>`
- option plus `ToArrowArray` throws
- per-chunk buffer aliasing still holds

### Step 5 — `test(perf)`: structural guard

`[Category("Performance")]` and `TimingGuards.RequireOptimizedBuildForTiming()`, Release only.

Asserts structural and allocation facts — flat `Slice` still returns `ColumnStorage<T>` and still aliases its parent; chunked `Slice` does not copy — plus one interleaved flat-versus-eight-chunk A/B run.

### Step 6 — `docs(arrow)`: roadmap

`docs/plan/ARROW-ROADMAP.md` Phase A and "Where we are today": record that the internal chunk layer exists, that chunk structure is preserved per column on the opt-in Arrow path, and that chunk-wise compute kernels remain open.

No pin changes — `docs/plan/` is outside the scanned scope, and no citation goes into a scanned document.

## 8. Risks

1. **`new Table(schema, columns)` behaviour is asserted from reflection and upstream source, not yet executed.** Step 0 is the mitigation and must pass before Step 4.
2. **Chunking buys structure, not compute.** Arithmetic on a chunked column pays one cached contiguous copy per operand. Recorded in the roadmap; chunk-wise kernels are a follow-up.
3. **`AsWritableSpan` throwing** is only safe if nothing in `src` calls it on an arbitrary storage. Audit before Step 2 lands and confirm the audit is clean.
4. **`NullMask` materialisation in a hot path** would allocate for no-null chunked columns, so the empty-span short-circuit is load-bearing and gets its own test.
5. **Chunk-count growth** if a future caller feeds chunked columns into streaming concat. Current call sites do not; document rather than cap.
