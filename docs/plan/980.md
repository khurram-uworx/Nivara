# #980 — Reproducible evaluation baseline over `docs/` (Phase 0, #916-A)

## 1. Goal

Turn the existing #915 label machinery into an explicit, versioned acceptance baseline: the
chunk ids, the query split, and the fixed-vs-baseline metrics must be reproducible from the
same corpus and seed, and a stale label file must fail loudly instead of quietly lowering every
ranker's score.

Acceptance criteria from the issue:

- The same corpus + seed produces the same chunk ids, split and baseline metrics.
- Coverage below 50% causes an explicit refusal, not silent degradation.
- No `src/Nivara` changes.
- Docs/whitespace/snippet gates stay green.

Scope is sample-only: `samples/NivaraChat` plus `tests/Nivara.Tests/Samples`. No PDF
extraction, no ANN index, no core storage or kernel changes.

## 3. Findings (measured 2026-11-08)

### F1 — Corpus hash is enumeration-order dependent

`RagIndexCache.ComputeContentHash` hashes file bytes in the order given and never mixes in the
file names. `MultiViewIndex.BuildAsync` builds that list with `Directory.GetFiles(..., AllDirectories)`
and appends the sample README last. Directory enumeration order is not specified (and differs
between Windows NTFS and Linux `readdir`), so:

- the content hash can differ for an identical corpus;
- chunk row order differs, which changes candidate row indices and the `Rank` tie-break
  (`OrderByDescending(score).ThenBy(index)`), so metrics can differ on exact float ties.

### F2 — Corpus hash ignores file names

Renaming a document leaves the content hash unchanged while every chunk id in it changes.
Cache validity is then saved only by `DocsMaxMtime`, which a rename need not move.

### F3 — Cache filename and manifest are machine-specific

`MultiViewIndexCache.ComputeHash` hashes the absolute `docsDir` string, and the manifest stores
the absolute `DocsDir`. Cache file names therefore differ per checkout path. This does not
affect the metrics (a rebuild is deterministic once F1/F2 are fixed), but it makes the printed
artifact path non-portable.

### F4 — Chunk identity is positional and undocumented

`ChunkId = relativePath#ordinal` is deterministic for a fixed `(content, chunker version, chunk
size)`, but any edit renumbers later chunks. `ChunkerVersion` is validated by the cache
(`MultiViewIndexCache.cs:106`) but not by label files, so a chunker bump can keep a judge cache
at 100% "coverage" while pointing at different chunks. This contract is the one the whole eval
set rests on and it is stated nowhere.

### F5 — Fixture has one dangling target

`samples/NivaraChat/relevance-fixture.tsv` (40 queries, 88 rows, 35 document targets) points one
row at `docs/RELEASE14-REVIEW.md`, deleted in `2473419c` ("remove superseded v1.4 release
review"). The committed fixture is therefore 87/88 resolvable today, not the 88/88 recorded in
`samples/data/nivarachat/learn/rag-learn-report.md`.

### F6 — Auto labels are stale by construction

`samples/NivaraChat/queries.tsv` (499 rows) references 7 documents that no longer exist
(`docs/blog/*` reorganised into `blog/bert` and `blog/rag`, plus `RELEASE14-REVIEW.md` and
`TODO.md`) and is keyed by `path#ordinal`. `EvalGroundTruth.Load` reads the committed file, so
`--labels auto` runs against a snapshot rather than deriving from the current corpus. The
coverage gate will refuse it, which is correct but needs documenting along with the refresh path.

### F7 — The judge cache has no provenance

`samples/data/nivarachat/eval/relevance.tsv` today holds 21,092 rows / 452 queries / 2,060 chunk
ids / 50 documents. It is keyed by `path#ordinal` and carries no corpus hash or chunker version,
so staleness can only be inferred from the 50% coverage heuristic. `RagEvalLabels.Load` already
skips `#` comment lines, so a provenance header is backward compatible.

### F8 — The refusal is not machine-observable

`RagLearnMode` prints the refusal and returns; the process exit code stays 0. Nothing downstream
can tell a refusal from a successful run. `RagLearnMode.ParseLabelKind`, the precedence rules
and the coverage gate have no unit tests.

### F9 — Baseline metrics are not recorded

`fixed(default)` and `fixed(content-only)` are computed on the test split only (2 queries for the
fixture) and written only when `--report` is passed. There is no structured, byte-stable record
and no corpus identity next to the numbers, so "the same corpus + seed gives the same baseline"
is asserted nowhere.

## 4. Proposed implementation

### A. Deterministic corpus identity

1. Add `MultiViewIndex.DiscoverCorpusFiles(docsDir, readmePath)` returning the markdown list
   ordered by full path (ordinal), with the README inserted in sort order. Use it in
   `MultiViewIndex.BuildAsync` and in `RagSearch` so the two caches hash the same canonical list.
2. Change `RagIndexCache.ComputeContentHash(IReadOnlyList<string> mdFiles, string repoRoot)`:
   order by repo-relative path, then hash `relativePath \0 fileBytes \0` per file. Fixes F1 and
   F2 and removes absolute paths from the hash. Update the four call sites
   (`RagIndexCache.IsValid/TrySave`, `MultiViewIndexCache.IsValid/TrySave`).
3. Add a `CorpusIdentity` record in `MultiViewIndex.cs`:
   `ContentHash`, `FileCount`, `ChunkCount`, `ChunkerVersion`, `ChunkSize`, `DocsDir`
   (repo-relative when under the repo root), `Backend`, `Dimension`. Capture it after the index
   resolves, so it works on both the cache-hit and rebuild paths.
4. Print one identity line per run (files, chunks, chunker, chunk size, content hash, backend,
   model dimension).
5. Document on `MultiViewIndex` and `MultiViewChunk`:
   - identity is `(SourcePath, ordinal, ChunkerVersion, ChunkSize)`;
   - ordinals are positional on purpose (judge labels key on them);
   - any change to chunker output requires a `ChunkerVersion` bump;
   - the path-keyed fixture is the edit-stable escape hatch.
6. Leave F3 as a documented limitation (normalising it needs `SchemaVersion++`; not required by
   the acceptance criteria).

One-time effect: changing the hash format invalidates every existing `rag_*_cache` file. The
next run rebuilds; this must be stated in the design note and the commit message.

### B. Labels

1. Move `LabelKind`, `ResolvedLabels` and `RetrievalLabels` from `RetrievalTrainingData.cs` into
   a new `samples/NivaraChat/Helpers/RetrievalLabels.cs` (pure move, matches the issue's
   deliverable and gives the contract one home). `TrainingQuery`, `CandidatePool`,
   `TrainingSetBuilder` and `QuerySplit` stay where they are.
2. Extract precedence into a pure function with today's semantics:

   ```text
   SelectSource(string? requested, bool judgeCacheExists) -> LabelKind
       requested null/blank -> judgeCacheExists ? Judge : Fixture
       "judge" | "fixture" | "auto" -> that value
       anything else -> ArgumentException (message names the accepted values)
   ```

   A judge file that exists but is empty stays a loud failure; it must not silently fall back to
   the fixture, because that changes what the numbers mean.
3. Move the threshold to `RetrievalLabels.MinimumCoverage = 0.5` and add
   `Accepts(ResolvedLabels)`. Keep `RagLearnMode.MinimumLabelCoverage` as a forwarding constant.
4. Document the three sources as a table in the class XML doc — path, key, grade scale,
   stability under docs edits, leakage caveat, precedence, and how to refresh. `Describe()`
   remains the single runtime string.
5. Refusal path: keep the wording, add a stable `REFUSED:` marker line, and set
   `Environment.ExitCode = 2` so the refusal is observable by scripts and CI logs.
6. Fixture hygiene: delete the `docs/RELEASE14-REVIEW.md` row (the doc was retired as fully
   actioned; `RELEASE15-REVIEW.md` is a retrospective, not a readiness checklist). Coverage
   becomes 87/87.

### C. Baseline record

1. Add `RetrievalBaseline` to `RetrievalEvaluation.cs`: schema version, `CorpusIdentity`, label
   kind / description / source path, matched/total/coverage/is-complete, seed, k, candidates,
   split counts, and the two fixed baselines over **both** scopes:
   - all resolved usable label queries (the wide, stable starting point);
   - the held-out test split (the scope the learned comparisons use).
   No timestamps: byte-identical output for identical inputs is the property being recorded.
2. Serialize with `System.Text.Json` (`WriteIndented = true`); doubles round-trip by default.
3. Default write path `samples/data/nivarachat/eval/baseline-{kind}-s{seed}-k{k}.json`
   (gitignored), with `--baseline <path>` override. Add the flag to `Program.cs`, the help text,
   `ModeContext` and the README flag table.
4. Add a `## Baseline (reproducible starting point)` section to the markdown report with the
   identity, the label line and both scopes.

Full-set fixed metrics are not leakage: the fixed weights never see labels. Learned models keep
being scored on the test split only.

### D. Design note and README

- `samples/NivaraChat/916-A.md`, mirroring `915.md`: what "reproducible" means here; the chunk
  identity and corpus-hash contract with the failures it prevents (F1–F6); the label-source table
  and precedence; the coverage gate and its exact output; the baseline schema and default path;
  the commands to reproduce; what "same corpus + seed" pins and what it does not (model files,
  backend, chunker version, chunk size, label file, seed); and the known limits (2-query test
  split for the fixture, stale judge cache, Silk numerical drift, uncommitted model).
- README `--rag-learn` section: a short reproducibility paragraph, a link to `./916-A.md`, the
  new flag, the "files written" entry and the updated file-tree listing for `RetrievalLabels.cs`.
- `docs/plan/980.md` is not in the snippet-gate or doc-reference scan scope (`docs/plan/` is
  excluded), so this document adds no pins. The README **is** scanned for `docs/*.md` references
  and `File.cs:NN` citations, so the README edits add neither.

## 6. Gates and verification

```text
dotnet format Nivara.slnx whitespace --verify-no-changes --no-restore
dotnet test tests/Nivara.Tests/Nivara.Tests.csproj -c Release --filter "FullyQualifiedName~Nivara.Tests.Samples"
dotnet test tests/Nivara.Tests/Nivara.Tests.csproj -c Release --filter "FullyQualifiedName~Nivara.Tests.Docs"
```

The Docs namespace is included because `samples/NivaraChat/README.md` is inside the doc-reference
scan even though it is not snippet-gated.

Then one fixture-mode sample run to record the real baseline — **after** the README edit, because
the README is part of the corpus and changes its own chunk ids and the content hash:

```text
dotnet run --project samples/NivaraChat -c Release -- --rag-learn --labels fixture --epochs 1
```

A judge-mode run (`--labels judge`) is the first measurement of F7's staleness; if it refuses,
that is the finding, not a failure.

## 7. Open decisions (recommendations first)

1. **Chunk identity**: keep positional `path#ordinal` and pin it in docs/tests (recommended), or
   add a content-derived chunk hash now (cache schema v2 plus a judge re-grade)?
2. **Judge-cache provenance**: add a `# corpus=… chunker=… chunkSize=…` header to `relevance.tsv`
   written by `RagEvalLabels.Save` and refuse on mismatch (recommended), or keep the 50% heuristic
   as the only signal?
3. **Baseline artifact**: always write JSON to the gitignored default (recommended), or only when
   `--report` is given? Committing a baseline file is not recommended: it depends on the
   uncommitted `samples/data/minilm` model, so CI could never verify it.
4. **Refusal exit code**: set `Environment.ExitCode = 2` (recommended), or keep exit 0 and rely
   on the printed marker?
5. **Fixture stale row**: delete the `RELEASE14-REVIEW.md` row (recommended), or retarget it to
   `RELEASE15-REVIEW.md` even though that document is a retrospective?
6. **Stale `queries.tsv`**: document the regeneration path and leave it refusing (recommended), or
   regenerate it in this change (needs MiniLM, and it goes stale on the next docs edit)?

## 8. Acceptance-criteria mapping

| Criterion | Covered by |
| --- | --- |
| Same corpus + seed → same chunk ids | A1, A5, identity tests, chunker repeat test |
| Same corpus + seed → same split | existing `QuerySplit_IsReproducibleAndPartitionsEveryQuery` |
| Same corpus + seed → same baseline metrics | A1–A4, C1–C2, hash/order/baseline determinism tests |
| Coverage < 50% → explicit refusal | B2, B3, B5, gate tests, exit code |
| No `src/Nivara` changes | all edits under `samples/NivaraChat` and `tests/Nivara.Tests/Samples` |
| Docs/whitespace/snippet gates green | no new `docs/*.md`; README adds no doc links or citations; format + Docs tests |

## 9. Non-goals

No PDF extraction. No ANN index or vector database. No `src/Nivara` storage or kernel changes.
No regeneration of the auto-label snapshot. No machine-independent cache names (F3) in this
change. No benchmark run.

## 10. Risks and one-time effects

- The content-hash change invalidates all existing `rag_*_cache` and `rag_multiview_cache` files;
  the first run rebuilds. Expect the printed cache path and the chunk row order to change once.
- Sorting the corpus changes candidate row indices; a metric can move only on exact float ties.
  The recorded baseline must be captured after all corpus edits, including the README.
- Moving `RetrievalLabels` changes using directives only; no behaviour change.
- A fixture-integrity test fails in CI when a cited document is retired, which is the point, but
  it couples the fixture to `docs/` renames — the fixture row must be fixed in the same change as
  the rename.
