# #980 — Reproducible evaluation baseline over `docs/` (Phase 0, #916-A)

## 1. Goal

Turn the existing #915 label machinery into an explicit, versioned acceptance baseline: the
chunk ids, the query split, and the fixed-vs-baseline metrics must be reproducible from the
same corpus and seed, and a stale label file must fail loudly instead of quietly lowering every
ranker's score.

Acceptance criteria from the issue:

- The same corpus + seed produces the same chunk ids, split and baseline metrics.
- Coverage below 50% causes an explicit refusal, not silent degradation.
- Every label artifact (`queries.tsv`, `relevance.tsv`) can be deterministically regenerated by
  the sample via a documented switch, and re-running on the same corpus + model is byte-identical.
  Both now live under `samples/data/nivarachat/` (gitignored, generated); only code/docs are
  tracked. There is no longer a separate fixture file or committed label artifact.
- No `src/Nivara` changes.
- Docs/whitespace/snippet gates stay green.

Scope is sample-only: `samples/NivaraChat` plus `tests/Nivara.Tests/Samples`. No PDF
extraction, no ANN index, no core storage or kernel changes.

## 3. Findings (measured 2026-11-08)

### F1 — Corpus hash is enumeration-order dependent

`RagIndexCache.ComputeContentHash` hashes file bytes in the order given and never mixes in the
file names. `MultiViewIndex.BuildAsync` builds that list with `Directory.GetFiles(..., AllDirectories)`
and appends the sample README last. Directory enumeration order is not specified (and differs
between Windows NTFS and Linux `readdir`), so:

- the content hash can differ for an identical corpus;
- chunk row order differs, which changes candidate row indices and the `Rank` tie-break
  (`OrderByDescending(score).ThenBy(index)`), so metrics can differ on exact float ties.

### F2 — Corpus hash ignores file names

Renaming a document leaves the content hash unchanged while every chunk id in it changes.
Cache validity is then saved only by `DocsMaxMtime`, which a rename need not move.

### F3 — Cache filename and manifest are machine-specific

`MultiViewIndexCache.ComputeHash` hashes the absolute `docsDir` string, and the manifest stores
the absolute `DocsDir`. Cache file names therefore differ per checkout path. This does not
affect the metrics (a rebuild is deterministic once F1/F2 are fixed), but it makes the printed
artifact path non-portable.

### F4 — Chunk identity is positional and undocumented

`ChunkId = relativePath#ordinal` is deterministic for a fixed `(content, chunker version, chunk
size)`, but any edit renumbers later chunks. `ChunkerVersion` is validated by the cache
(`MultiViewIndexCache.cs:106`) but not by label files, so a chunker bump can keep a judge cache
at 100% "coverage" while pointing at different chunks. This contract is the one the whole eval
set rests on and it is stated nowhere.

### F5 — Single label file (resolved)

The separate `relevance-fixture.tsv` is retired in favour of a single `relevance.tsv`. There is
one label file, generated by Ollama (`--rag-eval --ollama`) and human-editable; regeneration
simply overwrites it. The old fixture's dangling target (`docs/RELEASE14-REVIEW.md`) and its
87/88 coverage quirk no longer apply. `--labels fixture` is kept as a deprecated alias for
`--labels judge` (both read `relevance.tsv`) for CLI compatibility.

### F6 — Auto labels are stale by construction

`samples/data/nivarachat/queries.tsv` (499 rows) references 7 documents that no longer exist
(`docs/blog/*` reorganised into `blog/bert` and `blog/rag`, plus `RELEASE14-REVIEW.md` and
`TODO.md`) and is keyed by `path#ordinal`. `EvalGroundTruth.Load` reads the generated file, so
`--labels auto` runs against a snapshot rather than deriving from the current corpus. The
coverage gate will refuse it, which is correct but needs documenting along with the refresh path.

### F7 — The judge cache has no provenance

`samples/data/nivarachat/eval/relevance.tsv` today holds 21,092 rows / 452 queries / 2,060 chunk
ids / 50 documents. It is keyed by `path#ordinal` and carries no corpus hash or chunker version,
so staleness can only be inferred from the 50% coverage heuristic. `RagEvalLabels.Load` already
skips `#` comment lines, so a provenance header is backward compatible.

### F8 — The refusal is not machine-observable

`RagLearnMode` prints the refusal and returns; the process exit code stays 0. Nothing downstream
can tell a refusal from a successful run. `RagLearnMode.ParseLabelKind`, the precedence rules
and the coverage gate have no unit tests.

### F9 — Baseline metrics are not recorded

`fixed(default)` and `fixed(content-only)` are computed on the test split only and written only
when `--report` is passed. With the single `relevance.tsv` (hundreds of queries) the test split
is no longer the 2-query fixture split, but there is still no structured, byte-stable record and
no corpus identity next to the numbers, so "the same corpus + seed gives the same baseline" is
asserted nowhere.

### F10 — No deterministic regeneration path for the label artifacts

The two label artifacts the sample depends on have no documented, reproducible regeneration
command:

- `samples/data/nivarachat/queries.tsv` (auto labels) regenerates implicitly inside `RagEvalMode`
  when the file is missing (`DeriveFromChunks` + `Save`), but this is undocumented, silently
  overwrites, and there is no flag to request it deliberately.
- `samples/data/nivarachat/eval/relevance.tsv` (judge cache) is produced by `--rag-eval --ollama`,
  but ordering/normalisation of its rows is not pinned, and there is no provenance header.

There is no longer a separate fixture file: `relevance.tsv` is the single grade file. A human
evaluator (or a fresh checkout) therefore cannot deterministically rebuild either artifact, and
the generated copies drift from the corpus with no recorded refresh procedure. The 980
acceptance criteria require reproducibility of the baseline, which is impossible while the
inputs themselves have no regeneration path.

## 4. Proposed implementation

### A. Deterministic corpus identity

1. Add `MultiViewIndex.DiscoverCorpusFiles(docsDir, readmePath)` returning the markdown list
   ordered by full path (ordinal), with the README inserted in sort order. Use it in
   `MultiViewIndex.BuildAsync` and in `RagSearch` so the two caches hash the same canonical list.
2. Change `RagIndexCache.ComputeContentHash(IReadOnlyList<string> mdFiles, string repoRoot)`:
   order by repo-relative path, then hash `relativePath \0 fileBytes \0` per file. Fixes F1 and
   F2 and removes absolute paths from the hash. Update the four call sites
   (`RagIndexCache.IsValid/TrySave`, `MultiViewIndexCache.IsValid/TrySave`).
3. Add a `CorpusIdentity` record in `MultiViewIndex.cs`:
   `ContentHash`, `FileCount`, `ChunkCount`, `ChunkerVersion`, `ChunkSize`, `DocsDir`
   (repo-relative when under the repo root), `Backend`, `Dimension`. Capture it after the index
   resolves, so it works on both the cache-hit and rebuild paths.
4. Print one identity line per run (files, chunks, chunker, chunk size, content hash, backend,
   model dimension).
5. Document on `MultiViewIndex` and `MultiViewChunk`:
   - identity is `(SourcePath, ordinal, ChunkerVersion, ChunkSize)`;
   - ordinals are positional on purpose (judge labels key on them);
   - any change to chunker output requires a `ChunkerVersion` bump;
   - there is no longer a path-keyed escape hatch: `relevance.tsv` is keyed by chunk id, so any
     docs edit that renumbers chunks invalidates labels and the coverage gate must catch it.
6. Leave F3 as a documented limitation (normalising it needs `SchemaVersion++`; not required by
   the acceptance criteria).

One-time effect: changing the hash format invalidates every existing `rag_*_cache` file. The
next run rebuilds; this must be stated in the design note and the commit message.

### B. Labels

1. Move `LabelKind`, `ResolvedLabels` and `RetrievalLabels` from `RetrievalTrainingData.cs` into
   a new `samples/NivaraChat/Helpers/RetrievalLabels.cs` (pure move, matches the issue's
   deliverable and gives the contract one home). `TrainingQuery`, `CandidatePool`,
   `TrainingSetBuilder` and `QuerySplit` stay where they are.
2. Extract precedence into a pure function with the single-file semantics:

   ```text
   SelectSource(string? requested, bool judgeCacheExists) -> LabelKind
       requested null/blank -> judgeCacheExists ? Judge : throw (no label source available;
                            run --rag-eval --ollama, or pass --labels auto)
       "judge" | "auto" -> that value
       "fixture" -> Judge   (deprecated alias, kept for CLI compatibility)
       anything else -> ArgumentException (message names the accepted values)
   ```

   A judge file that exists but is empty stays a loud failure; with a single label file there is
   no fixture to fall back to, so the refusal (plus the regeneration guidance from E.6) is the
   correct behaviour.
3. Move the threshold to `RetrievalLabels.MinimumCoverage = 0.5` and add
   `Accepts(ResolvedLabels)`. Keep `RagLearnMode.MinimumLabelCoverage` as a forwarding constant.
4. Document the two sources as a table in the class XML doc (judge = `relevance.tsv`, auto =
   `queries.tsv`) — path, key, grade scale, stability under docs edits, leakage caveat,
   precedence, and how to refresh. `Describe()` remains the single runtime string. Note that the
   retired fixture was the only document-path-keyed source.
5. Refusal path: keep the wording, add a stable `REFUSED:` marker line, and set
   `Environment.ExitCode = 2` so the refusal is observable by scripts and CI logs.
6. Single label file: `relevance.tsv` is the only grade file. Ollama generates/overwrites it
   (`--regenerate judge`); humans may edit it in place; no separate fixture file or fixture
   label source remains.

### C. Baseline record

1. Add `RetrievalBaseline` to `RetrievalEvaluation.cs`: schema version, `CorpusIdentity`, label
   kind / description / source path, matched/total/coverage/is-complete, seed, k, candidates,
   split counts, and the two fixed baselines over **both** scopes:
   - all resolved usable label queries (the wide, stable starting point);
   - the held-out test split (the scope the learned comparisons use).
   No timestamps: byte-identical output for identical inputs is the property being recorded.
2. Serialize with `System.Text.Json` (`WriteIndented = true`); doubles round-trip by default.
3. Default write path `samples/data/nivarachat/eval/baseline-{kind}-s{seed}-k{k}.json`
   (gitignored), with `--baseline <path>` override. Add the flag to `Program.cs`, the help text,
   `ModeContext` and the README flag table.
4. Add a `## Baseline (reproducible starting point)` section to the markdown report with the
   identity, the label line and both scopes.

Full-set fixed metrics are not leakage: the fixed weights never see labels. Learned models keep
being scored on the test split only.

### D. Design note and README

- `samples/NivaraChat/916-A.md`, mirroring `915.md`: what "reproducible" means here; the chunk
  identity and corpus-hash contract with the failures it prevents (F1–F4, F6); the label-source
  table (judge, auto) and precedence; the coverage gate and its exact output; the baseline schema
  and default path; the commands to reproduce; what "same corpus + seed" pins and what it does not
  (model files, backend, chunker version, chunk size, label file, seed); and the known limits
  (no edit-stable escape hatch now that the fixture is retired, stale judge cache, Silk numerical
  drift, uncommitted model).
- README `--rag-learn` section: a short reproducibility paragraph, a link to `./916-A.md`, the
  new flag, the "files written" entry and the updated file-tree listing for `RetrievalLabels.cs`.
- `docs/plan/980.md` is not in the snippet-gate or doc-reference scan scope (`docs/plan/` is
  excluded), so this document adds no pins. The README **is** scanned for `docs/*.md` references
  and `File.cs:NN` citations, so the README edits add neither.

### E. Deterministic artifact regeneration

Add a first-class, documented regeneration path so a human (or CI) can rebuild every label
artifact deterministically. Introduce a switch `--regenerate <kind>` (with `kind` ∈
`queries | judge | all`) that works with the existing modes and is a no-op for the
run's normal work (it only writes the artifact, then exits):

1. `--regenerate queries` — runs the corpus build, invokes `EvalGroundTruth.DeriveFromChunks`,
   and writes `queries.tsv` (or the path given by `--queries`) with **stable, sorted output**
   (queries ordinal by query text; chunk ids within a row ordinal by chunk id; no trailing
   blank line beyond the final newline). Prints the count and the corpus content hash. This
   makes the currently implicit regeneration in `RagEvalMode` explicit and idempotent.
2. `--regenerate judge` — runs `--rag-eval` grading (`--ollama --model` required) but writes
   the judge cache in **canonical order** (queries ordinal, then chunk ids ordinal) with a
   provenance header line `# corpus=<contentHash> chunker=<ChunkerVersion> chunkSize=<n>
   backend=<backend> dimension=<n>` (backward compatible — `RagEvalLabels.Load` already skips
   `#` lines). Refuses to overwrite an existing cache unless `--force` is given, so a stale
   cache is never silently clobbered.
3. `--regenerate all` — runs `judge` then `queries` in that order, so a single command rebuilds
   the whole label set from a corpus + model. Writes a short manifest
   `samples/data/nivarachat/eval/regeneration-manifest.json` recording the corpus identity,
   model name, seed, counts, and the two output paths (no timestamps — byte-stable).
5. Determinism contract for all three: no timestamps, sorted rows, LF line endings, UTF-8
   without BOM, single trailing newline. Re-running on the same corpus + model must produce a
   byte-identical file (verified by the tests below). Model-dependent output (judge grades) is
   deterministic only for a pinned model + temperature; document that `--temperature` defaults
   to 0.0 for regeneration and that the model name is recorded in the manifest.
6. Missing-artifact guidance: whenever `queries.tsv` or `relevance.tsv` cannot be found, the
   sample prints a short, copy-pasteable regeneration command (and, when stdin is a TTY,
   offers an interactive `Regenerate now? [y/N]` prompt that runs the equivalent of
   `--regenerate`) instead of failing silently. `RagEvalMode` announces auto-derivation
   (`queries.tsv not found; deriving from corpus chunks`) and `RagLearnMode` prints the exact
   `--rag-eval --ollama --model ...` command when the judge cache is absent. No artifact is
   overwritten without either `--regenerate`/`--force` or explicit confirmation.
7. Add the flag to `Program.cs`, `ModeContext`, the help text and the README flag table, and
   document the procedure in `samples/NivaraChat/916-A.md` (new "Regenerating the artifacts"
   section) with the exact commands, the review step, and the commit guidance (one commit per
   regenerated artifact, so a diff shows only the intended change).

No fixture file remains; the fixture-integrity test and the `CommittedFixture_EveryTargetDocumentExists`
test are dropped. `LoadFixture` may stay as an internal utility but is no longer a label source.

## 7. Open decisions (recommendations first)

1. **Chunk identity**: keep positional `path#ordinal` and pin it in docs/tests (recommended), or
   add a content-derived chunk hash now (cache schema v2 plus a judge re-grade)?
2. **Judge-cache provenance**: add a `# corpus=… chunker=… chunkSize=…` header to `relevance.tsv`
   written by `RagEvalLabels.Save` and refuse on mismatch (recommended), or keep the 50% heuristic
   as the only signal?
3. **Baseline artifact**: always write JSON to the gitignored default (recommended), or only when
   `--report` is given? Committing a baseline file is not recommended: it depends on the
   uncommitted `samples/data/minilm` model, so CI could never verify it.
4. **Refusal exit code**: set `Environment.ExitCode = 2` (recommended), or keep exit 0 and rely
   on the printed marker?
5. **Stale `queries.tsv`**: document the regeneration path and leave it refusing (recommended), or
   regenerate it in this change (needs MiniLM, and it goes stale on the next docs edit)?
6. **Regeneration switch**: a single `--regenerate <queries|judge|all>` flag (recommended), or
   separate `--regen-queries` / `--regen-judge` flags? A single flag keeps the CLI surface small.
   Either way, the manifest and determinism contract are unchanged.
7. **Human editing**: since `relevance.tsv` is the single file and regeneration overwrites it,
   should regeneration refuse to overwrite a file with uncommitted edits (git-dirty check), or
   always overwrite with `--force`? Overwrite-with-force is simpler and matches the user's stated
   preference; the git-dirty guard prevents accidental loss.

## 9. Non-goals

No PDF extraction. No ANN index or vector database. No `src/Nivara` storage or kernel changes.
No machine-independent cache names (F3) in this change. No benchmark run. Regeneration of the
label snapshots is now in scope (§E), but only as a deterministic, documented, human-reviewed
procedure — not as an automatic CI step, and not as a silent overwrite of existing files.

## 10. Risks and one-time effects

- The content-hash change invalidates all existing `rag_*_cache` and `rag_multiview_cache` files;
  the first run rebuilds. Expect the printed cache path and the chunk row order to change once.
- Sorting the corpus changes candidate row indices; a metric can move only on exact float ties.
  The recorded baseline must be captured after all corpus edits, including the README.
- Moving `RetrievalLabels` changes using directives only; no behaviour change.
- Retiring the fixture removes the only document-path-keyed label source: `relevance.tsv` is keyed
  by chunk id, so any docs edit that renumbers chunks invalidates labels and the coverage gate
  (plus the regeneration guidance) must catch it. A regeneration must be reviewed as a diff and
  committed separately from code changes, or the baseline numbers move without anyone noticing.
- Model-dependent regeneration is not byte-stable across model versions; the manifest records the
  model name and temperature so a change is at least detectable.
- With a single label file there is no offline fallback on a fresh checkout: `--labels judge`
  refuses until `--rag-eval --ollama` has produced `relevance.tsv`. Document this in the
  quick start and the missing-artifact guidance (E.6).
