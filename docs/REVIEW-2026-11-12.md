| | |
|---|---|
| **Base commit** | `2881a92386de5c3498b91488199e23e4e1bf5afc` (branch `main`, 2026-11-12) |
| **Version reviewed** | 1.5.0 |
| **Scope** | `src/Nivara` (199 files, 50,701 lines, 182 public types), `src/Nivara.Extensions` (80 files, 24,978 lines, 108 public types), both package definitions, the three workflows, the reader-facing docs, and `docs/adr/` |

This document is the record of the review. Each finding is filed as an issue carrying the `high` or `medium` label and the `review` label; the issue holds the reproduction, the file-and-symbol evidence, the acceptance criteria, and the related history. This document holds the reasoning, the cross-cutting themes, and the ordering.

---

## 1. Scope and method

**What was read.** All of `src/Nivara` and `src/Nivara.Extensions`: storage (`ColumnStorage`, `Chunk`/`ChunkedColumn`, factories), column and frame kernels, the query layer (plan, operations, execution strategies, the fused expression engine and its kernel IR), the typed LINQ layer, AutoDiff, metrics, diagnostics, the streaming and memory-budget machinery, the I/O adapters, the BLAS seam, the Silk/OpenCL backend and the AI/model layer. Then the public surface as a whole: which types are public, which are documented as extension points, and what a consumer can actually reach.

**How it was judged.** Against three questions, in this order:

1. *Does the advertised behaviour hold?* Null semantics, immutability, schema stability, streaming budgets, async execution. Where a claim was testable, it was tested rather than reasoned about.
2. *What does the public surface commit the project to?* Public types are contracts. Every public type was assessed as either deliberate (documented, tested, conformance-tested) or accidental (an implementation detail that leaked).
3. *What breaks the first time this is used in production?* Data-dependent failures, disposal that invalidates other objects, caches that grow forever, and errors that are swallowed.

**What was verified empirically.** H1, H2 and H3 were reproduced on the base commit with a throwaway NUnit fixture (Release build), then the fixture was deleted and the tree left clean. The exact observed messages are in those issues. H4, H5, H6, H8 are structural defects that do not reproduce deterministically on x64; they were established by reading the code paths and are argued from the interleavings, not from a run. Everything else is static analysis with file-level evidence.

**One finding was deliberately not filed.** The review also examined the concentration of heavy and prerelease dependencies in the single `Nivara.Extensions` package. That finding was left out of the filed set at the requester's instruction, which is why the numbering runs H1-H7 and then M1-M16 rather than filling H8. No issue was created for it.

**What this review did not do.** No benchmark run, no full-suite run, no allocation or throughput profiling, no third-party security audit of the dependency graph, no API review of the samples. Where a performance claim is made below, it is structural (an operation that must do a dictionary lookup per cell) rather than measured; the issues say which is which.

## 3. High findings

### H1 - The typed query layer cannot express a null comparison

`Where(r => r.Name == null)` does not run. It throws a wrapped `QueryExecutionException` at `Collect()` with "Comparison Equal operation requires compatible types. Left operand type: String, Right operand type: Object".

The path is short and entirely mechanical: the LINQ translator maps `ExpressionType.Equal` straight onto a `ComparisonExpression`, a `ConstantExpression` with a null value becomes a `LiteralExpression` whose `ResultType` is `typeof(object)`, and comparison validation refuses the pair because it only attempts coercion for *non-null* literals. The kernel lowerer would additionally null-dereference on the same node (`literal.Value!`), so the failure is caught one layer earlier than it would otherwise appear - validation saves it from an NRE and reports a schema error instead.

Why this is High and not Medium: null filtering is the single most common predicate on a nullable column, and it is the operation the library's positioning is built on ("explicit null handling, no NaN-based semantics"). A user who reads the README and writes the obvious query gets an execution-time failure that names `Object`, which tells them nothing about the fix. The failure also cannot degrade gracefully: there is no fallback path, because the node never gets past validation.

The fix is structural, not a coercion widening: a null test is a mask operation, not a value comparison. A dedicated node (`IsNull`/`IsNotNull`) with `bool` result type, lowered and evaluated by reading the mask only, removes the whole class of problem and makes the semantics explicit (`IsNotNull` is never null, unlike SQL's `NOT (x = NULL)`).

### H2 - Empty results change a column's runtime type

`FilterByMask` with an all-false mask, `Take(0)`, and the "no rows matched" branch of `Skip` all rebuild columns from `IColumn.ElementType`. Since `ElementType` reports the *underlying* type for a mask-based nullable column, the empty frame holds `NivaraColumn<int>` where the source held `NivaraColumn<int?>`. `GetColumn<int?>` then throws `ColumnTypeMismatchException`, and `Schema` reports `Int32` for both frames, so nothing warns the caller.

This is the worst shape a bug can take in a data pipeline: it is data-dependent. The same query succeeds on a full result and throws on an empty one, so it passes review, passes tests with sample data, and fails in production on the day a filter matches nothing. Because the failure mode is an exception on a *read*, it surfaces far from the operation that caused it.

The fix direction is already established in the codebase: `ColumnFilterHelper.ConcatenateColumns` explicitly preserves nullable element types. The empty-column path was simply not updated when the mask-based representation landed. Carrying the column's constructor type on the column instance (`IColumn.CreateEmpty()`) removes the reflection-and-lose-nullability path entirely.

### H3 - Disposing a derived frame destroys the source frame

`WithColumn`, `SelectColumns`, `WithoutColumn` and friends build a new frame over the **same** `IColumn` instances. `NivaraFrame.Dispose()` disposes every column it holds. So disposing the derived frame marks storage disposed underneath the source frame, and the next read throws `ObjectDisposedException` naming `NivaraColumn`, not the frame that did it.

The same defect was already found and fixed once for query frames: a `QueryFrame` created by `AsQueryFrame` used to dispose the source frame's columns and now does not. The frame-to-frame case was not covered by that fix, and no test disposes a derived frame and then reads the source.

This is a public-contract problem before it is a bug: `NivaraColumn.Dispose` has no reference counting, so two frames cannot both own one column. "Immutable data model" holds only until someone writes `using`. The three candidate resolutions (non-owning derived frames, copy-on-derive, or removing `IDisposable` from frames) are a design decision that should be recorded as an ADR, and the ownership rule belongs in the XML docs of `NivaraFrame.Dispose` either way.

### H4 - The foundational storage type publishes lazy caches without synchronisation

`ColumnStorage<T>` memoises a zero-copy `Tensor<T>` view and a string hash array in plain fields. `AsTensor` checks for null, allocates, and assigns with no barrier - on ARM64 a reader can see the reference before the tensor is initialised, and two threads can each build a view that the class remarks promise is built once. `TryGetHashCodes` is hand-rolled double-checked locking on a non-volatile field, with the final read **outside** the lock.

The reasoning that makes this easy to miss is written in the class: the storage is immutable, therefore caching is safe. Immutability of the *contents* says nothing about publication of the *cache*.

Severity is High because of blast radius, not frequency. Every column, every slice, every chunk sits on this type. A wrong hash array does not crash - it produces a wrong group key or a wrong sort order, silently. The writable tensor path used by optimisers can hand two callers different `Tensor<T>` objects over one buffer.

The fix is small and standard: `LazyInitializer.EnsureInitialized` or `Volatile` publication for the tensor view, and the same for the hash array with the reads inside the publication boundary. If the memoisation is not a required contract, deleting the caches is even simpler. What must change either way is the class remark, which currently states a thread-safety property the code does not provide.

### H5 - The stream budget can deadlock, and it hides over-release

`MemoryBudget.Release` calls `waiter.Registration?.Dispose()` inside `lock (gate)`. The registration callback takes `lock (budget.gate)`. `CancellationTokenRegistration.Dispose()` waits for an in-flight callback. So a cancellation that races a release deadlocks: the releasing thread holds the gate and waits for the callback; the callback waits for the gate.

The window is narrow but it sits exactly where the budget matters - a caller cancelling a streaming query under memory pressure. In a server that is a leaked request thread and a budget that never recovers. `Dispose()` has the same shape, so teardown can hang too.

Separately, `current = Math.Max(0, current - releasedBytes)` turns an over-release into silent accounting. Every caller that releases more than it acquired has a bug, and the clamp makes that bug invisible while letting the next `AcquireAsync` hand out capacity that is still in use - the cap stops being a cap.

Both are cheap to fix: collect registrations to dispose inside the lock and dispose them after releasing it (the pattern the abandoned-resource cleanup already tries to follow), and turn the clamp into a loud failure or a diagnostic counter.

### H6 - The public memory advice is not about memory

`NivaraFrame.GetMemoryRecommendations()` returns `MemoryRecommendations.AvailableMemory`, documented as "available memory in bytes" and assigned from `GC.GetTotalMemory(false)` - the managed heap. The thresholds it classifies against are declared in kilobytes, and one carries the comment "20KB (more appropriate for test data)". A 40 KB frame is therefore reported as "very large" and a 32 GB machine is reported as having a few megabytes available.

The consequence is not a crash, it is worse: advice that is wrong at every realistic scale trains users to ignore it, including on the day a frame genuinely exceeds RAM. This is also consumer-facing API, so the shape is frozen as soon as anyone depends on it - the cost of getting it wrong goes up with time, not down.

The streaming `MemoryBudget` already models the right thing (a caller-supplied limit). Either derive the recommendation from that, with a property name that says what it means, or remove the number and keep the classification relative to a configured budget.

### H7 - A minor release removed public API with no deprecation channel

`rg "Obsolete" src/` returns nothing. 1.5.0 removed `DataFrameSchemaValidationException`, split `SchemaValidationException` into two types, renamed the `NivaraColumn` factory to `NivaraColumnFactory`, and removed the legacy `ExpressionEvaluator`, the dead AutoDiff exceptions, and the array-based tensor conversions. The changelog is the only migration notice.

Deleting genuinely dead public surface is good hygiene - and 1.5.0 was right to do it. What makes this a finding is that there is no mechanism: no `[Obsolete]` bridge in the release that removed them, no API baseline, no analyzer, and no documented statement of whether `1.x` minors are allowed to break. A rename like factory → `NivaraColumnFactory` is the textbook case for one obsolete period plus a forwarding shim; it costs one minor version and removes the break entirely.

This compounds with M2. Without an API baseline, the project cannot tell a deliberate break from an accidental one, so the next break will also be discovered by a consumer.

## 4. Medium findings

### M1 - The XML documentation is written and then discarded

Both library projects have thorough `///` comments and neither sets `GenerateDocumentationFile`. The produced `.nupkg` contains `lib/net11.0/Nivara.dll` and `README.md` and nothing else - no `.xml`. So 290 public types, including every documented exception and every null-semantics remark, are invisible in IntelliSense. The content already exists; it is being thrown away at build time. One property, plus a decision on `CS1591`, plus a package-content assertion.

### M2 - No API baseline, and the plan model is public

There is no `PublicAPI.Shipped.txt`, no `Microsoft.CodeAnalysis.PublicApiAnalyzers`, no `ApiCompat` step, and no test that enumerates the exported surface. At the same time `IQueryOperation`, `IQuerySource`, `QueryPlan`, `QueryNode`, `ColumnExpression` (with a `protected set` on `ResultType`) and `AggregationFunction` are public and documented as extension points. The planning layer cannot be refactored without a break, and a break will not be detected. Either adopt the analyzer and declare the seam in an ADR, or make the planning model internal and keep the frame as the contract.

### M3 - `Equals` is three different operations

`NivaraColumn<T>.Equals(T)` and `.Equals(NivaraColumn<T>)` return `NivaraColumn<bool>` - an element-wise comparison that looks like equality at the call site. `NivaraFrame.Equals(object?)` is overridden to `ReferenceEquals`, so two identical frames are "not equal" and `Distinct()`/`HashSet` do nothing useful. `Schema.Equals` is structural but ignores metadata. Three types, three meanings, one word; and the column operator set is asymmetric (`Equals` exists, `NotEquals`/`>=`/`<=` do not).

### M4 - Diagnostics are global, unbounded and serialised

`DiagnosticsTracker` is one static `bool` and one static `List<OperationDiagnostics>` behind one lock. Enabled once, it grows for the life of the process, with no cap and no eviction; `GetRecordedOperations()` copies the whole list under the lock; every recorded operation from a parallel query serialises on it. `ExecutionDiagnostics` already exists with the right scope, so the global sink is a duplicate with worse properties.

### M5 - The abandoned-resource manager is unreachable, slow and inverted

`NivaraResourceManager` is declared `static class` (internal) with every member `public`, so the feature cannot be enabled by a consumer and the public members are dead. Inside: `UntrackResource` is an O(n) scan of a `ConcurrentDictionary` under a global lock on every frame dispose (O(n²) across n disposals); `CleanupAbandonedResources` runs cleanup actions **inside** the lock while a comment above claims it runs outside; `Disable()` drops tracked resources without running their cleanup. `ConditionalWeakTable` gives the O(1) semantics the current design is imitating.

### M6 - Unbounded expression caches, and a lossy cache key

The fused engine keeps **eight** static `ConcurrentDictionary` caches, none with a capacity, TTL or eviction path; the main one holds a compiled delegate per distinct expression, with literals baked in as `Expression.Constant`. A service that builds queries per request accumulates delegates forever. The signature that keys those caches is built by formatting literal values with `IFormattable.ToString(null, InvariantCulture)`, which renders `DateTime`, `TimeOnly` and `TimeSpan` without fractional seconds - so two expressions differing by milliseconds share a cache entry, and the second silently computes with the first literal. This is the precision half of the cache-collision issue fixed in an earlier release; the type half was fixed, the value half was not.

### M7 - Disposal errors are swallowed on the explicit path

`QuerySourceHandle.Release`/`ReleaseAsync` wrap disposal in a bare `catch { }`, and the XML docs now say so ("disposal errors are swallowed"). Best-effort swallowing is defensible for *abandoned* cleanup; it is not defensible when a caller writes `using` around a query over a Parquet writer, because a failed flush then reports success and loses buffered rows with no signal anywhere. A second bare `catch { }` sits on the streaming producer path.

### M8 - The BLAS seam's explicit path is a comment

`NivaraBlas.UseBlas(string? path, ...)` accepts `path`, documents "bound to path", and never uses it - the code says so in a comment ("override the resolver? For now, the resolver handles auto-discovery"). `OpenBlasInterop.ExplicitPath` is declared and never assigned, so its loader branch is dead. The provider is registered in process-global statics, and `openblas_set_num_threads` is called on every `MatMul`/`Gemv`, mutating a global other libraries in the process may share. Set the thread count once at registration, honour the path, and scope the registration.

### M9 - The async API is async in name

`Collect()` is `CollectAsync(default).GetAwaiter().GetResult()`, and `CollectAsync` awaits `engine.ExecuteAsync` **without** `ConfigureAwait(false)` - so on a UI thread with a `SynchronizationContext`, `Collect()` deadlocks the first time the await yields. `IQueryOperation.ExecuteAsync`'s default implementation ignores the token entirely; the concrete overrides check it at entry and then run a synchronous `Execute`, so a long `Filter` cannot be cancelled. `IQuerySource.ExecuteAsync`'s default runs `Execute()` on the calling thread and wraps it in `Task.FromResult`. The streaming strategy uses `ConfigureAwait(false)` throughout, so the gaps elsewhere look accidental rather than deliberate.

### M10 - No AOT or trimming posture, and unannotated reflection

Nothing declares `IsAotCompatible`, `IsTrimmable`, or `RequiresUnreferencedCode`, while roughly thirty call sites close generic methods over runtime types (`MakeGenericMethod` in the column factory, filter helper, numeric dispatcher, group-key readers, fused evaluator, frame extensions and metrics), and the typed LINQ layer reflects over row-type properties. `Nivara.Extensions` also carries `Microsoft.ML`, which is not trimming-friendly, so the package cannot be trimmable while it ships as one package. The posture needs to be stated per package, the reflection annotated, and a trimmed publish added to CI so the claim is testable. Four exception filters written as `ex.GetType().Name.Contains("Csv")` belong in the same sweep.

### M11 - Several vocabularies for one operation

`ToObjects`, `ToRows` (an alias whose body is `=> ToObjects()`) and `ToList`. Three `AsStream` overloads declared identically on both `QueryFrame` and `NivaraQuery<T>`, plus two `Collect`/`CollectAsync` pairs. `SelectColumns` on the frame and `Select` as an extension doing the same thing, while `Select` on `QueryFrame` is a different operation and `Select` in LINQ means row projection. `Filter`, `Where(Func<NivaraRow,bool>)` and `Where(Expression<Func<T,bool>>)` are three filtering stories. Four `GroupBy` overloads on two receivers, nine join overloads, and two column-construction paths. Each addition is defensible alone; together they make the correct method undiscoverable, and the duplicated streaming surface has to be maintained twice.

### M12 - Row access is the slow path with no warning

Every cell read through `NivaraRow` does a case-insensitive string dictionary lookup (`StringComparer.OrdinalIgnoreCase` re-hashes the key per access) and, for nullable-element columns, a `ConcurrentDictionary` lookup plus `MakeGenericType` inside `IsNullableColumnFor` - per cell, not per column. `NivaraRow.ColumnNames` allocates `[.. map.Keys]` on every read. The object indexer boxes. The `Func<NivaraRow,bool>` overload is the only filtering API that takes ordinary C#, so it is the one a user reaches for in a loop, and it is dramatically slower than the expression path with nothing in the signature to say so.

### M13 - Packaging mechanics

`GeneratePackageOnBuild` is true in both libraries, so every build writes a package at a hardcoded version; the reviewed working tree's `bin/Release` holds both a 1.5.0 and a stale 2.0.0-preview package. The version is declared in two `.csproj` files, overridden by a workflow variable, and again by the tag - three places, documented in `RELEASING.md` as something a human keeps in sync. There is no `global.json` (SDK floats within `11.0.x`), no central package management (`Microsoft.SourceLink.GitHub` is pinned at 10.0.301 centrally and overridden to 11.0.100 in seven projects), no lock file, and no package validation or content assertion.

### M14 - CI/CD coverage

One `ubuntu-latest` leg, so a library with SIMD kernels, native library loading and path handling is never tested on Windows or ARM64 - and H4 is only observable on a weak memory model. Coverage is uploaded with `fail_ci_if_error: false` and has no threshold. The `Category=ReleaseReadiness` suite is excluded from CI and the workflow that runs it is `workflow_dispatch`-only, so it first runs at publish time - after the tag exists. CD holds `contents: write` without needing it and has no `environment:` approval gate, yet it publishes to nuget.org. There is no Dependabot, no CodeQL, and no vulnerability check on a dependency set that includes native interop and a protobuf-generated ONNX surface.

### M15 - The docs describe a repository that no longer exists

`RELEASING.md` requires a `NUGET_API_KEY` secret that the workflow does not use (it publishes via OIDC), and tells the reader to check a `global.json` that does not exist. `AGENTS.md` states that dependency versions are "deliberately unpinned" while every reference carries an exact version, and carries measured figures ("66 tests, ~25 s", "3873 tests", "p99 0.1 s") that are used to justify a policy threshold and that nothing re-checks. Its AutoDiff link points at a root `AUTODIFF.md` that does not exist, and the reference gate cannot catch it because it only resolves paths beginning `docs/`. The README promises "errors surface early, not at runtime" while H1/H2 throw at `Collect()`.

### M16 - The frame cannot be iterated

`NivaraFrame` implements `IFrame : IDisposable` and is not `IEnumerable<NivaraRow>`: no `GetEnumerator`, no `GetRow(int)`, no `Rows`. `NivaraRow` is public, has an internal constructor, and is created in exactly one place - inside the `Where(Func<NivaraRow,bool>)` predicate loop - so a consumer can never hold one. Every sibling type is enumerable (`NivaraColumn<T>`, `NivaraSeries<T>`, `DataLoader<T>`), and `NivaraFrame.FromRows<T>` covers the input direction. Anyone writing a CSV/JSON/Excel exporter or a "print the first five rows" helper must reimplement the row abstraction.

## 5. Cross-cutting themes

Four themes recur across the findings, and each is worth more than the sum of the issues.

**1. Contracts that are stated in prose and not enforced in code.** The `ColumnStorage` remarks promise a single memoised tensor view (H4). `Iframe`/`NivaraFrame` docs imply frames own what they dispose (H3). `MemoryRecommendations.AvailableMemory` says bytes (H6). `UseBlas(path:)` says bound to path (M8). `AGENTS.md` says versions float (M15). The pattern is a doc comment describing the intended design, with the implementation never revisited after a change. The documentation gate verifies that citations resolve - which is a real achievement - but it cannot tell whether a sentence is true. A short "claims audit" in the release checklist, one that compares doc statements against the csproj and the workflows, would catch this class earlier than a review.

**2. The empty/degenerate case is systematically untested.** H2 is the clearest instance: an all-false mask, zero rows, a `Take(0)`. It is also the shape of `Dispose` on a frame with shared columns (H3), of a query whose filter matches nothing, and of an all-null column in the typed path (H1). The test suite is large (4,347 test declarations) and overwhelmingly exercises populated frames. A deliberate "degenerate input" suite - zero rows, all-null, single row, duplicate keys, disposed object - would pay for itself immediately.

**3. Ownership is undefined, so every resource story is local.** Frames dispose columns they did not create (H3). The abandoned-resource manager is unreachable and cannot arbitrate (M5). The explicit disposal path swallows failure because the abandoned path does (M7). The memory budget governs bytes but has a publication bug and a clamp (H5). The recommendation API invents a third notion of "available memory" (H6). One ownership ADR - who owns a column, who owns a source, who owns a buffer, and what dispose means for each - would resolve four issues and prevent their successors.

**4. The public surface is what leaked, not what was designed.** The plan model is public (M2); nine join overloads, three materialisation verbs and six stream overloads exist (M11); an internal manager has public members (M5); a public row type is unreachable (M16); a public recommendation API is frozen in a shape nobody would choose (H6); the package ships no XML docs for any of it (M1); and a minor release removed parts of it without a deprecation path (H7). An API baseline plus one written rule - *public means documented, tested, and supportable* - is the smallest change that stops the growth.

## 6. What is working well

This matters for prioritisation: the review should not be read as a case for rework.

- **The storage design is good.** A single `ColumnStorage<T>` with a sole-owner array, an optional byte-wise null mask, zero-copy slicing and a lazy tensor view is the right core, and ADR-007's decision to keep the byte-wise mask canonical in core with bit-packing only at the Arrow boundary is a well-argued call. H4 is a publication bug in that design, not a flaw in it.
- **The documentation gates are genuinely strong.** Symbol-anchored citations resolved with Roslyn (ADR-008), a snippet gate with an explicit authoring contract (ADR-005), coverage pins whose arithmetic is written down, and an ADR index gate that checks both directions. Most projects have none of this. M15 asks to extend the gates, not to trust them less.
- **The null semantics are explicit and mostly honoured.** Byte-wise masks, SQL-like comparison semantics, null propagation spelled out per kernel. H1 is one missing node in a design that is otherwise coherent; H2 is one code path that missed the mask-based migration.
- **The ADR set is short and load-bearing.** Ten ADRs, each recording a real decision with alternatives, and the code mostly follows them. The gaps (ownership, versioning, public-surface policy) are exactly the decisions that have not been recorded - which is why they are the ones that drifted.
- **The kernel work is deliberate.** `TensorPrimitives` behind `KernelSelector` with a documented threshold, span-first boundaries in AutoDiff, a reusable SIMD probe project, and benchmark hygiene rules (distributions not single estimates, Release-only measurement) that most performance-conscious codebases never write down.
- **The test suite is broad** (4,347 declarations across 408 files) with conventions that are followed rather than aspirational, including the discipline of not asserting on wall-clock in the default suite.

## 7. Recommended order of work

The ordering is by *cost of being wrong*, not by severity label.

1. **H2 first.** It is data-dependent, it throws on a read, and it is a small fix (`IColumn.CreateEmpty()` carrying the constructor type). A regression test for the all-false mask closes a class, not a case.
2. **H3, with the ownership ADR.** It is a public-contract break already shipped; every day it stays, the chance that a consumer has built on the current behaviour grows. The ADR is the work; the code change is small afterwards.
3. **H5 and H4 together.** Both are concurrency-publication defects in infrastructure. H5's deadlock is reachable from a cancelled stream today; H4's race needs ARM64. Fixing both and adding one stress test category covers the pair.
4. **H1.** Design it as `IsNull`/`IsNotNull` nodes in the kernel IR, not as a validation relaxation. It is the highest-visibility user-facing defect and the cheapest to demonstrate fixed.
5. **H7 plus M2.** They are one decision: an API baseline, a deprecation policy, and a written public-surface rule. Do them before the next release, because the next release is when the second break happens.
6. **H6, M1, M5, M7.** Public-facing correctness and honesty: a recommendation API that means something, docs that ship, a manager that either exists or does not, and disposal that reports failure.
7. **M13 and M14.** Reproducible packaging and a CI that can fail. These unlock the verification needed for M10 and M2.
8. **M3, M4, M6, M8, M9, M11, M12, M15, M16.** Real, prioritised by how much surface each freezes. M15 is the cheapest and should be done continuously; M16 is the most user-visible gap in the public API.

Two combinations are worth doing as single pieces of work rather than as issue-by-issue changes: **M3 + M11 + M16** (one public-API vocabulary pass, since all three change the same surface and each is breaking on its own), and **M10 + M13** (one packaging pass, since the package split determines what can be trimmable).
