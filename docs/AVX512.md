# AVX512 in Nivara's CPU attention path

This document records how AVX512 was specially handled in the CPU decode attention
path, why that special-casing was folded into the fused online-softmax pass, and
what replaced it.

## What was specially handled

`AttentionKernels<T>.DecodeAttention` originally computed every score for a query
head, softmaxed the whole row, then weighted the value rows. The floating-point
V accumulation had a dedicated AVX512 routine, `VPhaseFloat512`, alongside a
portable `Vector<T>` routine, `VPhaseFloat`.

`VPhaseFloat512` processed the head dimension in 16-lane `Vector512<float>`
blocks. For each block it accumulated across all KV positions in one `zmm`
register: it broadcast the scalar softmax weight for a KV row, loaded the
corresponding 16 value lanes, and applied `FusedMultiplyAdd` into the
accumulator. Positions where `headDim` was not a multiple of 16 were handled by a
scalar tail loop. The portable path did the same with `Vector<float>`, sized to
the host (SSE2/AVX2/NEON).

## Why it was removed as a standalone path

The two-pass shape (all scores, softmax, then V) required materialising every
score in a rented `scores` buffer and reading the KV cache more than once. The
fused online-softmax pass in Milestone 2 of issue #658 walks each KV row once,
maintaining a running maximum and renormalising the accumulator when a larger
score appears. That removes the score buffer and changes the control flow enough
that the old standalone V-phase routines no longer fit: they assumed all weights
were already final before accumulation began.

Keeping a separate AVX512 V-phase also duplicated the weight/accumulator logic
and made the allocation and parity contracts harder to reason about.

## What replaced it

The floating-point path now performs the same per-row V accumulation inside the
online-softmax loop:

- when hardware supports it, each `headDim` block is updated with
  `Vector512<float>.FusedMultiplyAdd` using a broadcast weight;
- otherwise the portable `Vector<float>` path is used;
- remaining lanes are handled by a scalar tail.

The generic path (Half, BFloat16, and other `IFloatingPointIeee754<T>` types)
uses the identical scalar online update with `TensorPrimitives.Dot` and `T.Exp`,
so the numerical contract is shared across types. Prefill attention
(`BatchedAttention`) is unchanged and still uses the tiled GEMM kernels from
Milestone 1.
