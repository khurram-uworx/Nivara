# ADR-002 Review & Execution Plan (2026-08-06)

Working plan for reviewing the library from the point of view of
[ADR-002 — AutoDiff Keeps the NivaraColumn Span Boundary](docs/adr/002-autodiff-span-boundary.md)
and closing the gaps found. Companion ADRs:
[ADR-001 (non-nullable domain)](docs/adr/001-autodiff-nonnullable-domain.md),
[ADR-003 (batch in fused ops)](docs/adr/003-batch-fused-ops-not-rank-n-primitives.md).

## Verdict: ADR-002 is implemented and honored — no storage fork

Every decision point in ADR-002 holds today:

| ADR-002 requirement | Status | Location |
|---|---|---|
| `GradTensor<T>.Data` = `NivaraColumn<T>`, with `ToColumn()` | Done | `src/Nivara/AutoDiff/GradTensor.cs` |
| `GradKernels.cs` pure span kernels over `IFloatingPointIeee754<T>` | Done | `src/Nivara/AutoDiff/Operations/GradKernels.cs` (30+ kernels) |
| Ops compute over spans, wrap results once | Mostly done | see F2 below |
| `OpNode<T>.BackwardFunction` = `Action<NivaraColumn<T>>` | Done | `OpNode.cs` |
| `ComputationGraph.Backward` = `NivaraColumn<T>?` | Done | `ComputationGraph.cs` |
| Raw `Tensor<T>` backing declined | Done | zero `Tensor<T>` storage in AutoDiff (views only) |
| `IsNull(int)` removed from tensor surface | Done | only boundary `HasNulls` throws (ADR-001) |

The `GradKernels` layer landed in 1.2.0 (Tasks 1–6). What follows is
**divergence cleanup + hardening**, not an architecture change.

## Findings (divergence from the ADR's intent)

### F1 — Kernel entry layer: a documented split, not a churn phase

`ReverseGradOperations` calls `TensorsHelper.MultiplyCore` / `TensorsHelper.Transpose`
directly (~28×, e.g. `ReverseGradOperations.cs:264,281,290`) for matrix ops,
while forward-mode ops route MatMul/Transpose through `GradKernels`
(`ForwardGradOperations.cs:220-286`). `GradKernels.MatMul` / `Transpose` are thin
forwarders to the same `TensorsHelper` methods (`GradKernels.cs:443-449`).

**Layering decision (resolved by documentation, not by rerouting calls):**
`TensorsHelper` is the shared matrix-kernel store with BCL swap targets (ADR-003),
callable directly by matrix-heavy ops. `GradKernels` is the AutoDiff facade that
forward-mode and elementwise/softmax ops route through. The reverse-op direct
`TensorsHelper` calls are accepted divergence — the same spirit as the `MatMul`
`T[]` exception below. The one capability gap is that `GradKernels` cannot express
`bTransposed: true` matmul; expose it in P1a.

**Documented exception (not drift):** `GradKernels.MatMul` takes the output as a
`T[]` (not `Span<T>` like every other kernel) because the underlying parallel
tiled kernel requires a captured array — spans cannot cross `Parallel` lambda
boundaries. This is intentional and recorded so it does not read as a
signature inconsistency.

**Resolved:** the hand-rolled `Sigmoid` / `Tanh` / `SoftMax` family in
`TensorsHelper` (platform-duplicating re-implementations with `.NET 11` swap
comments, sole production caller `BCEWithLogitsLoss.cs:47`) was deleted;
`BCEWithLogitsLoss` now calls `GradKernels.Sigmoid` (`BCEWithLogitsLoss.cs:46`),
a thin `TensorPrimitives.Sigmoid` delegate. AutoDiff activations are now
platform delegates only — aligned with the EXAMPLES.md "integrate, don't fight
the platform" positioning.

### F2 — Backward gradient accumulation still copies owned arrays (~50 spots)

Freshly-allocated gradient arrays are wrapped with `NivaraColumn<T>.Create(arr)`
(a copy) instead of `CreateFromOwnedArray` (zero-copy). Sites include
`ReverseGradOperations.cs:92,129,161,167,206,220,285,294,366,379,904,1010,1175,1216,1246,1274`,
`BCEWithLogitsLoss.cs:51,58`, `AdaptiveAvgPool2d.cs:53`, `TypeConverter.cs:43`.
`BCEWithLogitsLoss` additionally copies both inputs into fresh arrays just to read
them (`BCEWithLogitsLoss.cs:18-21`) instead of consuming spans directly. MHA
already does it right (`ReverseGradOperations.cs:566-570,769-773`). Aggregate
counts: reverse ops 67 `Create` vs 13 `CreateFromOwnedArray`; forward ops 12 vs
37. This is exactly the ADR-002 "wrap results once" (`ResultTensor`) pattern.

⚠️ **Safety rule:** each site must be audited so the array is a freshly
allocated `new T[...]` that is not reused or returned after wrapping. Never wrap
`ArrayPool`-rented scratch buffers (e.g. `bTArr` / `aTArr` / `gTArr`).

### F3 — Columnar reductions leak into the domain

- `Sum` calls `a.Data.Sum()` — `ReverseGradOperations.cs:1033`, `ForwardGradOperations.cs:311`
- `Mean` calls `a.ToSeries().Average()` — materializes a `NivaraSeries` in the
  non-null domain — `ReverseGradOperations.cs:1061-62`, `ForwardGradOperations.cs:338-39`
- Tangent sums `a.Tangent!.Sum()` — `ForwardGradOperations.cs:317,345`
- KL sum `klElements.Sum()` — `ReverseGradOperations.cs:2231`, `ForwardGradOperations.cs:729`

These should be `TensorPrimitives.Sum(span)` over `AsSpan()`. Column null-mask
semantics (all-null → zero, etc.) do not apply in the non-null domain.

### F4 — Duplicated row-softmax

`AttentionKernels.SoftmaxRows` / `SoftmaxRow` (`AttentionKernels.cs:53-59`)
re-implements the row-softmax logic in `GradKernels.Softmax` / `SoftmaxSingle`.
Two kernels to keep in parity.

### F5 — `GradKernelsTests` coverage is thin vs the kernel surface

31 tests in `tests/Nivara.Tests/AutoDiff/GradKernelsTests.cs`, mostly float
KnownValues. Missing: Half for nearly everything, gradient kernels
(SigmoidGradient, TanhGradient, ReluGradient, LeakyReluGradient, GeluGradient,
GeluExactGradient, LogGradient, AbsGradient, ClipGradient, SoftmaxGradient,
LogSoftmaxGradient incl. single-row), non-square MatMul shapes, and error paths
(short output span). The ADR's "independently unit-testable" claim is not backed
by coverage.

> **BFloat16 coverage is deferred (net11, not now).** `System.Numerics.BFloat16`
> only exists on .NET 11; the whole solution targets net10.0, so it cannot even
> compile here. The AutoDiff kernels are generic over
> `IFloatingPointIeee754<T>` and will accept BFloat16 with no code change once we
> migrate. Today's BFloat16 support is *load-time widening* (BF16 file-format
> bytes → F32) in `samples/Nivara.Samples/SafeTensorsLoader.cs` (`ConvertBF16`),
> so there is no BFloat16-typed kernel path to test. Add BFloat16 kernel tests
> as part of the net11 migration, not before.

### F6 — Minor zero-copy misses

`ModuleHelpers.CreateBlockDiagonalMask` / `CreateCausalMask` wrap fresh arrays
via `Create` (`ModuleHelpers.cs:61,80`).

### F7 — Profiling gate

ADR-002's amendment says revisit storage (Options B/C) *only* with profiling
evidence that the wrapper dominates. The harness baseline
(`tests/Nivara.PerformanceTests/README.md`, point A 2026-08-05) shows
Linear fwd+bwd [32×256] = 1,492,187 B/op, 0.35 gen0/op — nothing proves the
wrapper dominates, so **no storage change is warranted today**. An isolation
scenario keeps the evidence on hand.

## Execution plan

### P0 — Zero-copy gradient/result wraps (F2 + F6)

Convert owned, freshly-allocated arrays from `NivaraColumn<T>.Create(arr)` (copy)
to `CreateFromOwnedArray(arr)` (zero-copy):

- `ReverseGradOperations.cs` — ~67 `Create` sites (backward accumulation + forward results)
- KL/VAE helpers: `ApplyKlElementWise` / `ApplyKlMeanGradient` /
  `ApplyKlLogVarGradient` / `ApplySampleNormalForward`
  (`ReverseGradOperations.cs:2398,2408,2422` + neighbors)
- `ForwardGradOperations.cs` (12 sites)
- `BCEWithLogitsLoss.cs` — grad wraps at `:52,59`, and the input read copies at
  `:19-22` become direct span reads (`logits.AsSpan()`, `targets.AsSpan()`)
- `AdaptiveAvgPool2d.cs:53`
- `TypeConverter.cs:43`
- `ModuleHelpers.cs:61,80`

Apply the F2 safety rule at every site. MHA is the model
(`ReverseGradOperations.cs:566-570,769-773`).

### P1a — Kernel-layer gap-fill (F1, trimmed)

1. Add the missing `GradKernels` surface the reverse ops need:
   `MatMulTransposedB` (forwards to `TensorsHelper.MultiplyCore(..., bTransposed: true)`),
   used by `MatMulTransposedB` forward + MHA QK^T. This is capability, not
   indirection — GradKernels currently cannot express transposed-B matmul.
2. Route `BCEWithLogitsLoss` through `GradKernels.Sigmoid` (`BCEWithLogitsLoss.cs:46`)
   so the loss module uses the same facade as the ops.
3. No call-site reroute: the ~27 remaining direct `TensorsHelper.*` matrix calls
   in `ReverseGradOperations` stay (see the F1 layering decision). The `MatMul`
   `T[]` output signature is a documented exception (see F1) — keep it.

### P1b — Span-based reductions (F3)

- `Sum`: `a.Data.Sum()` → `TensorPrimitives.Sum(a.AsSpan())`
- `Mean`: `a.ToSeries().Average()` → `TensorPrimitives.Sum(span) / T.CreateChecked(a.Length)`
- Tangent sums: `a.Tangent!.Sum()` → `TensorPrimitives.Sum` over tangent span
- KL: `klElements.Sum()` → span sum

Keep the existing empty-tensor throw guards first.

### P1c — Single row-softmax (F4)

Expose an in-place / buffer-friendly row variant of `GradKernels.Softmax` and
have `AttentionKernels.SoftmaxRows` / `SoftmaxRow` delegate to it (they operate
on rented score buffers, so the variant must not allocate). The current
`SoftmaxRow` is already SIMD for float/double — the consolidation must preserve
that path and the scalar Half/BFloat16 fallback.

### P1d — Single span-access idiom (F8)

**Dropped.** The `TryGetSpan` bool-discard is harmless; the churn in
`ReverseGradOperations` and `ModuleHelpers` has no enforcement value since the
boundary is already hard (F2). The `AsSpan()` accessor stays canonical where it
already exists; no migration.

### P2 — Kernel test hardening (F5)

Expand `GradKernelsTests.cs`:

- Half variants for float-tested kernels (Sigmoid, Tanh, Relu, Gelu, Exp, Log,
  Abs, Clamp, Negate, Divide, Softmax, LogSoftmax, MatMul). BFloat16 variants
  are deferred to the net11 migration — the type does not exist on net10.0
  (see the F5 note).
- Gradient kernels: SigmoidGradient, TanhGradient, ReluGradient,
  LeakyReluGradient, GeluGradient, GeluExactGradient, LogGradient, AbsGradient,
  ClipGradient, SoftmaxGradient, LogSoftmaxGradient (row-wise and single-row)
- MatMul: non-square shapes + bTransposed variant (once added in P1a)
- Error paths: short output span throws `ArgumentException`

Follow the existing KnownValues pattern; reference NivaraTorch fixtures where applicable.

### P3 — Wrapper-cost perf scenario (F7)

Add a scenario to `tests/Nivara.PerformanceTests` isolating the column+storage
wrapper cost per op (e.g. an N-op span chain vs the same ops on raw arrays,
measuring B/op and gen0/op). Record results into the point-A README table per
baseline policy. Only if it shows the wrapper dominates would we file an
ADR-002 amendment to revisit Option B — otherwise the finding is closed.

### P4 — No-regression gate & harness automation

Make the "no degradation" invariant (see below) executable rather than a
retrospective audit:

1. Add `--json` output to `tests/Nivara.PerformanceTests/Program.cs` — emit each
   scenario's `ops/s`, `B/op`, `gen0/op` as JSON.
2. Add a `--compare <baseline.json>` mode that exits non-zero when any scenario
   regresses beyond tolerance (see the gate criteria below).
3. Tolerance constants live in the harness: `ops/s` ≥ 90% of baseline, `B/op`
   and `gen0/op` non-increasing.
4. Wire the gate into the per-phase workflow; once stable, run it as a
   pre-commit / CI step so it cannot be skipped.

## No-regression gate (per-phase, non-negotiable)

**Invariant:** no phase ships if the harness shows a throughput regression or an
allocation increase beyond run-to-run variance on the same machine.

1. **Baseline.** Before starting each perf-relevant phase (P0, P1b) — and again
   for the parity phases (P1a, P1c) — run the harness on the current HEAD
   (3 runs, median, same machine, per the README methodology) and save the result
   as that phase's baseline.
2. **Measure.** Apply the phase, rebuild Release, run the identical harness on
   the same machine.
3. **Compare** scenario-by-scenario:
   - `ops/s` ≥ 90% of the baseline median (parity phases target ≥ 98%)
   - `B/op` non-increasing vs baseline (P0/P1b are expected to decrease it —
     record the win)
   - `gen0/op` non-increasing vs baseline
4. **Record.** Update the point-A README table with the new numbers per the
   existing baseline policy.
5. **Fail → halt.** Any scenario outside tolerance stops the phase; bisect to the
   offending change, fix, re-measure, and only then proceed to the next phase.
   After P4 lands the comparison is `--compare` against the saved baseline; until
   then it is the same-machine 3-run median process above.

Why a hard gate: point A is already a documented rolling baseline and the harness
lives in the repo — this turns "we should not degrade" into a checked, per-phase
constraint, and makes the P0/P1b allocation improvements proven rather than
assumed.

## Engineering expectations (2026-08-06)

- **Consistency:** positive — P0 standardizes the wrap pattern
  (forward/reverse asymmetry gone), P1a fills the kernel-layer gap,
  P1b removes the columnar leak, P1c removes the softmax duplication,
  and `BCEWithLogitsLoss` is folded into the same facade.
- **Performance:** yes, but calibrated. P0 is the substantive win (one fewer
  full-size allocation + memcpy per wrapped gradient/result array). P1b adds a
  smaller SIMD-reduction win. P1a/P1c are neutral. The only large lever
  (Option B/C storage swap) stays gated behind P3 evidence per ADR-002.

## Scope decisions (2026-08-06)

- F1 resolution: **documented layering decision** — reverse matrix ops keep
  calling `TensorsHelper` directly; `GradKernels` is the AutoDiff facade;
  `MatMulTransposedB` gap filled in P1a
- Plan scope: **P0 + P1 + P2 + P3 + P4 all in scope** (P1 = P1a gap-fill, P1b,
  P1c; **P1d dropped** — no enforcement value)
- Consistency refinements folded in: **`BCEWithLogitsLoss` in P0/P1a**,
  **documented `MatMul` `T[]` exception (F1)**,
  **kernel duplication (Sigmoid/Tanh/SoftMax) resolved — `TensorsHelper` family
  deleted, `BCEWithLogitsLoss` → `GradKernels.Sigmoid`**
- No-regression assurance: **P4 + per-phase gate** added — no phase ships with a
  throughput or allocation regression vs its same-machine baseline
