# Nivara API Surface Review (Follow-up)

Date: 2026-08-12
Reviewer: senior .NET engineering review (assisted)

This document captures findings from a follow-up review of the Nivara library and its
public API surface. It builds on the prior review at `docs/REVIEW.md` (2026-08-09).
All prior findings (#172-#181) are closed/resolved. All 19 findings
(#197-#215) identified here are resolved as of 2026-08-14.

## Scope

- Core library: `src/Nivara/` (columnar engine, query/execution, AutoDiff, IO, diagnostics)
- AutoDiff subsystem: `src/Nivara/AutoDiff/` (autograd engine, NN modules, optimizers, training)
- Tests: `tests/Nivara.Tests/`

## Overall Assessment

The 10 issues from the prior review (2026-08-09) are all closed. The core columnar
engine (`NivaraColumn<T>`, `NivaraSeries<T>`, `NivaraFrame`) is well-documented
(55 public members / 469 XML doc lines, 37 / 220, 37 / 247 respectively) and has
clean encapsulation. The primary gap is in the **AutoDiff subsystem**: a wide
public API surface (~55 files across modules, losses, optimizers, training,
serialization, initializers) with near-complete absence of XML doc comments,
plus several consistency and performance issues in AutoDiff internal code.

### 2. Boxing in Adam/AdamW SIMD kernels

`Adam.ApplyAdamToSpan` (`src/Nivara/AutoDiff/Optimizer/Adam.cs:60-75`) and
`AdamW.ApplyAdamWToSpan` (`src/Nivara/AutoDiff/Optimizer/AdamW.cs:46-91`) use the
`T → concrete-type` boxing pattern to pass generic `T` values to the typed SIMD kernels:

```csharp
(float)(object)lr!, (float)(object)wd!,
(float)(object)biasCorr1!, (float)(object)biasCorr2!,
(float)(object)beta1T!, (float)(object)beta2T!, (float)(object)epsT!
```

This allocates a boxed `object` on the stack for each of ~6 parameters per `Step()`
call. The same pattern repeats for `double` and `Half` branches.

**Fix:** Use `float.CreateChecked(lr)` / `double.CreateChecked(lr)` / `Half.CreateChecked(lr)`.
The `T.CreateChecked(...)` calls already used elsewhere in these methods (e.g.,
Adam.cs:57, AdamW.cs:43) show the pattern is known; the boxing is a leftover from
an earlier implementation.

**Resolved 2026-08-14 (issue #198, PR #219):** boxing removed from
`Adam.ApplyAdamToSpan` / `AdamW.ApplyAdamWToSpan` — the `(float)(object)lr!` casts
were replaced with `T.CreateChecked(...)` (commit 6a9b25f).

### 3. `OpNode<T>.Inputs` stored as `IReadOnlyList<object>`

`OpNode.cs:8`: `public IReadOnlyList<object> Inputs { get; }`

Every ReverseGradOperations method (e.g., `Add`, `Subtract`, `Multiply`, `Divide`,
`MatMul`, etc.) constructs `new object[] { a, b }` or `new object[] { a }`, boxing each
`ReverseGradTensor<T>` at op creation. This list is traversed by
`ComputationGraph.BuildBackwardPlan` (`ComputationGraph.cs:91-109`) and
`ZeroGrad`/`ClearGradients` to unbox each input back to `ReverseGradTensor<T>`.

Since `OpNode<T>` is already generic over `T`, `Inputs` should be
`IReadOnlyList<ReverseGradTensor<T>>`, eliminating both boxing at construction and
unboxing at traversal. This is the central node type in the computation graph — the
boxing affects every differentiable operation.

**Resolved 2026-08-14 (issue #199, PR #219):** `OpNode<T>.Inputs` re-typed as
`IReadOnlyList<ReverseGradTensor<T>>`, eliminating per-op boxing/unboxing at graph
construction and traversal (commit e966cc5).

### 4. Reflection in `NivaraColumn.Transform` / `TransformNonNull`

`NivaraColumn.Transform` (`NivaraColumn.cs:2370-2394`) and
`NivaraColumn.TransformNonNull` (`NivaraColumn.cs:2468-2492`) use reflection on every
call for nullable value-type result types:

```csharp
var nullableType = typeof(Nullable<>).MakeGenericType(typeof(TResult));
var nullableArray = System.Array.CreateInstance(nullableType, Length);
// ...
var nullableInstance = Activator.CreateInstance(nullableType, result[i]);
nullableArray.SetValue(nullableInstance, i);
// ...
return (NivaraColumn<TResult>)typeof(NivaraColumn<>)
    .MakeGenericType(typeof(TResult))
    .GetMethod(nameof(NivaraColumn<int>.CreateFromNullable), ...)
    .Invoke(null, new object[] { nullableArray })!;
```

This runs `Array.CreateInstance`, `Activator.CreateInstance`, `MakeGenericType`,
`GetMethod`, `MethodInfo.Invoke` on every `Transform` call that produces null results
with a value-type `TResult`.

**Fix:** Add a generic helper or pre-cache `MethodInfo` delegates keyed by `Type`.

**Resolved 2026-08-14 (issue #200, PR #219):** reflection dropped from
`NivaraColumn.Transform`/`TransformNonNull` and the `NivaraFrameExtensions` compute
helper — replaced with pre-cached generic delegates (commits 3423081, a8c24bc).

### 5. `Schema.areTypesCompatible` uses stale numeric type list

`Schema.cs:17-31` hardcodes 11 numeric types in a local array:
```csharp
var numericTypes = new[]
{
    typeof(byte), typeof(sbyte), typeof(short), typeof(ushort),
    typeof(int), typeof(uint), typeof(long), typeof(ulong),
    typeof(float), typeof(double), typeof(decimal)
};
```

This omits `Half`, `nint`, `nuint`, `Int128`, `UInt128`, `char` — all of which are
included in `TypeCompatibilityValidator.GetNumericTypes()` (`TypeCompatibilityValidator.cs:229-237`)
and `TypeExtensions.IsNumericType()` (`TypeExtensions.cs:8-29`). This is a
**three-way inconsistency** (noted as pending in prior REVIEW.md #13, lines 302-305).

**Impact:** e.g., `NivaraColumn<Half>` + `NivaraColumn<float>` are treated as
incompatible by `Schema.areTypesCompatible`, causing spurious type-mismatch errors in
cross-type arithmetic that should succeed per `TypeExtensions`/`TypeCompatibilityValidator`.

**Resolved 2026-08-14 (issue #201, PR #217):** `Schema.areTypesCompatible` now
delegates to `TypeCompatibilityValidator`, eliminating the stale three-way
inconsistency (commit a0b4218).

## Medium-Priority Findings

### 6. `Module<T>.Forward(input1, input2)` throws `NotSupportedException`

`Module.cs:15-18`: The base class provides a virtual `Forward(input1, input2)` that
always throws `NotSupportedException`. Only `MultiheadAttention` overrides it (with
`new`, see finding #7). This is a "silent API lie" — the method exists on the base
class but throws for all subclasses except one.

**Fix:** Either make it abstract on `Module<T>` (forcing subclasses to either implement
or not support multi-input), or have subclasses that don't support it not expose it
(i.e., move multi-input Forward to an optional interface).

**Resolved 2026-08-14 (issue #202, PR #220):** the throwing two-input virtual was
dropped from `Module<T>`; multi-input forward now lives on the optional
`IMultipleInputModule<T>` interface (commit a62c614).

### 7. `MultiheadAttention` hides base `Forward` with `new` keyword

`MultiheadAttention.cs:77`:
```csharp
public new ReverseGradTensor<T> Forward(ReverseGradTensor<T> input, ReverseGradTensor<T> paddingMask)
```

Uses `new` instead of `override`, **hiding** `Module<T>.Forward(input1, input2)`.
Calling this method via a `Module<T>` reference hits the base's
`NotSupportedException`. Calling via `MultiheadAttention<T>` works correctly.
This is a dispatch trap for generic module consumers.

**Fix:** Change `new` to `override`.

**Resolved 2026-08-14 (issue #203, PR #217):** `MultiheadAttention.Forward` is now an
`override`, restoring virtual dispatch through `Module<T>` references (commit ece2207).

### 8. Duplicated type-switch dispatch in `NivaraColumn`

`NivaraColumn.cs` contains ~360 lines of duplicated `typeof(T) == typeof(X)`
type-switching across multiple methods:
- `multiplyTensorPrimitive` (`NivaraColumn.cs:1500-1560`)
- `divideTensorPrimitive` (`NivaraColumn.cs:1570-1630`)
- `addTensorPrimitive` (`NivaraColumn.cs:1640-1700`)
- `subtractTensorPrimitive` (`NivaraColumn.cs:1710-1770`)
- `equalsTensorPrimitive`, `greaterThanTensorPrimitive`, `lessThanTensorPrimitive`
  (similar patterns)

`NivaraSeries.cs` has the same pattern in `sumTensorPrimitive` (~28 lines) and
`divideByCount` (~110 lines, `NivaraSeries.cs:102-183`).

Each method has a near-identical switch over 12+ types with `TensorPrimitives` calls.
The prior review (#157, now resolved) addressed the `NivaraColumn<T>` arithmetic
kernels to support the extended numeric domain, but the dispatch pattern itself is
duplicated.

**Fix:** Extract a dispatch table of pre-cached delegates (e.g.,
`ConcurrentDictionary<Type, Action<...>>`) or use a single generic `NumericTensorKernels<T>`
call per type via `MakeGenericMethod` + `Expression.Lambda` compilation.

**Resolved 2026-08-14 (issue #204, PR #221):** the duplicated type-switch dispatch in
`NivaraColumn` and `NivaraSeries` was collapsed onto a centralized
`NumericKernelDispatcher` (commits 0c592cb, ae40905, ff2f56c).

### 9. `ensureBuffer`/`EnsureBuffer`/`ensureVelocityBuffer` casing inconsistency

Three optimizer classes use different naming and visibility:
- `Adam.cs:31` — `void ensureBuffer(int idx, int size)` (implicit-private, lowercase `e`)
- `AdamW.cs:333` — `private void EnsureBuffer(int idx, int size)` (explicit private, uppercase `E`)
- `SGD.cs:100` — `void ensureVelocityBuffer(int idx, int size)` (implicit-private, lowercase `e`)

AGENTS.md specifies camelCase without `_` prefix for private fields, and the codebase
generally uses explicit `private` modifiers.

**Fix:** Standardize on `EnsureBuffer`/`EnsureVelocityBuffer` (PascalCase, explicit `private`).

**Resolved 2026-08-14 (issue #205, PR #227):** optimizer buffer helpers now use
explicit `private` and consistent casing (`EnsureBuffer`/`EnsureVelocityBuffer`)
(commit 0fcb77b).

### 10. `Sequential` constructor silently skips null modules

`Sequential.cs:11-24`: The constructor accepts `params Module<T>[] modules` and silently
filters out null entries (`if (m != null)`) without throwing or warning. This is
inconsistent with `Append()` (Sequential.cs:34-39), which correctly calls
`ArgumentNullException.ThrowIfNull`. A caller passing `new Sequential(linear, null, dropout)`
would silently get a 2-module sequential, with no error.

**Fix:** Use `ArgumentNullException.ThrowIfNull` for each module, or throw
`ArgumentException` listing the null index.

**Resolved 2026-08-14 (issue #206, PR #217):** `Sequential` constructor now throws
`ArgumentNullException` on null modules, matching `Append()` (commit 3338ae6).

### 11. `Loss<T>.Reduce` allocates 1-element `ReverseGradTensor` for scalar division

`Loss.cs:41-44`:
```csharp
case Reduction.Mean:
    int count = divisor ?? elementwiseLoss.Length;
    var scale = GradientUtils.Full(1, T.CreateChecked(count));
    return ReverseGradOperations.Divide(ReverseGradOperations.Sum(elementwiseLoss), scale);
```

`GradientUtils.Full(1, ...)` creates a full `ReverseGradTensor<T>` (allocates
`NivaraColumn` storage + creates a graph node) just to divide a scalar sum by a
scalar count. This is wasteful for the most common loss reduction path.

**Fix:** Add a `DivideByScalar` operation on `ReverseGradTensor<T>` that applies
`TensorPrimitives.Divide` to the data span and scales the gradient accordingly,
without graph construction.

**Resolved 2026-08-14 (issue #207, PR #225):** `ReverseGradOperations.DivideScalar`
(VJP) and a `ReverseGradTensor<T>.DivideByScalar` wrapper were added; `Loss<T>.Reduce`
Mean path now uses it instead of a 1-element graph tensor (commits 2897908, 90653e0,
101d2c5).

### 12. `GradientUtils.GetGraphInfo` returns `Dictionary<string, object>`

`ComputationGraph.cs:171` and `GradientUtils.cs:291`: Both return
`Dictionary<string, object>`, boxing all `int`/`bool` values into `object`.
The dictionary has 4 known keys: `TotalNodes` (int), `IsLeaf` (bool),
`RequiresGrad` (bool), `OperationCounts` (Dictionary<string, int>).

**Fix:** Return a strongly-typed record:
```csharp
public readonly record struct GraphInfo(int TotalNodes, bool IsLeaf, bool RequiresGrad,
    IReadOnlyDictionary<string, int> OperationCounts);
```

**Resolved 2026-08-14 (issue #208, PR #227):** `GetGraphInfo` now returns a typed
`GraphInfo` record instead of `Dictionary<string, object>` (commit 4b3b369).

### 13. Private fields use `_` prefix in AutoDiff training/nn files

AGENTS.md specifies: "Private fields: camelCase without `_` prefix." The core library
follows this. But 4 AutoDiff files use the `_`-prefix style:

- `TrainingLoop.cs:52-56`: `_model`, `_loader`, `_lossFn`, `_optimizer`, `_maxEpoch`
- `DataParallelTrainer.cs:12-17`: `_model`, `_loader`, `_lossFn`, `_optimizer`, `_epochs`, `_maxDegreeOfParallelism`
- `LayerNorm.cs:8-13`: `_normalizedShape`, `_eps`, `_affine`, `_weight`, `_bias`
- `MultiheadAttention.cs:9-20`: `_embedDim`, `_numHeads`, `_headDim`, `_attnScale`, `_causal`, `_qProj`, `_kProj`, `_vProj`, `_oProj`, `_attnDropout`

Notably, other AutoDiff files already follow the convention correctly (e.g.,
`Adam.cs` uses `beta1`, `beta2`, `eps` without prefix; `SGD.cs` uses `momentum`;
`Dropout.cs` uses `probability`).

**Fix:** Rename all `_`-prefixed fields to camelCase.

**Resolved 2026-08-14 (issue #209, PR #228):** `_`-prefixed private fields in
`TrainingLoop`, `DataParallelTrainer`, `LayerNorm`, and `MultiheadAttention` renamed
to camelCase (commits 66b6cf5, 5af6c26, d27ef8f).

### 14. `NivaraColumn` operators are asymmetric

`NivaraColumn.cs:2021-2048`: Only `*` (3 overloads) and `+` (1 overload) operators
exist. `-` (subtract) and `/` (divide) are available only as methods
(`Subtract()`, `Divide()`), not as operator overloads. This was noted as pending in
the prior REVIEW.md (#11, lines 263-264).

**Fix:** Add `operator -` and `operator /` overloads matching the existing `*`/`+` pattern.

**Resolved 2026-08-14 (issue #210, PR #221):** `-`, `/`, and `+` operator overloads
(plus scalar/reverse arithmetic methods) added to `NivaraColumn` (commit 772275a).

### 15. `TensorsHelper.RowNorms` / `ColumnNorms` orphaned dead code

### 16. `NivaraColumn.CreateFromNullable(Array)` takes non-generic `Array`

`NivaraColumn.cs:556`: `public static NivaraColumn<T> CreateFromNullable(Array values)`
accepts a non-generic `System.Array`, forcing runtime type inspection and boxing.
The null-mask copy path allocates a new `bool[]` per call.

**Fix:** Provide a generic overload `CreateFromNullable(T?[] values)` (already
exists at `NivaraColumn.cs:536` — the `Array` overload is a legacy entry point).
Consider marking the `Array` overload `[Obsolete]`.

**Resolved 2026-08-14 (issues #212 + #222, PRs #221/#223):** a generic static factory
`NivaraColumn.CreateFromNullable<T>` was added and callers migrated (commit 6ffc461);
the legacy non-generic `NivaraColumn<T>.CreateFromNullable(Array)` overload was then
removed outright as a breaking change (commit 6bbd0a0) — stronger than `[Obsolete]`.

### 17. `TrainingLoop<T>` / `DataParallelTrainer<T>` are unsealed

`TrainingLoop.cs:50`: `public class TrainingLoop<T>` (not sealed)
`DataParallelTrainer.cs:10`: `public class DataParallelTrainer<T>` (not sealed)

AGENTS.md specifies: "Sealed by default: use `sealed class` for non-abstract classes
unless inheritance is explicitly designed." The initial finding assumed neither class
has virtual/protected members, but investigation showed both classes DO expose a
designed `protected virtual` hook surface that is subclassed and asserted in tests:

- `TrainingLoop<T>`: `OnEpochStart`, `OnBatchEnd`, `OnEpochEnd`, `Dispose(bool)`
  (`TrainingLoop.cs:155-173`)
- `DataParallelTrainer<T>`: `OnEpochStart`, `OnEpochEnd` (`DataParallelTrainer.cs:267-268`)
- `HookTrackingTrainingLoop : TrainingLoop<float>` (TrainingTests.cs:431) — asserted by
  `TrainingLoop_VirtualMethods_AreCalled`
- `HookTrackingTrainer : DataParallelTrainer<float>` (DataParallelTests.cs:164) — asserted by
  `Run_Hooks_AreCalled`

**Resolved 2026-08-14 (issue #213, branch khurram/issues):** closed as not applicable.
The protected virtual hooks are an explicitly designed inheritance surface, which falls
under AGENTS.md's "unless inheritance is explicitly designed" carve-out; sealing would
break the test build and remove the hook-extension API. No code change. A future
refactor that replaces the hooks with public events/callbacks could then allow sealing.

### 18. `SGD.ensureVelocityBuffer` is implicit-private

`SGD.cs:100`: `void ensureVelocityBuffer(int idx, int size)` — missing explicit
`private` access modifier, relying on C# default accessibility for methods.
(Consistent with `Adam.cs:31` `void ensureBuffer` — both should be `private`.)

**Resolved 2026-08-14 (issue #214, PR #227):** optimizer buffer helpers gained
explicit `private` modifiers (commit 0fcb77b, same change as #205).

### 19. `Loss<T>.Reduce` — two `Forward` overloads with divergent `Reduce` call paths

`CrossEntropyLoss.Forward` (CrossEntropyLoss.cs:12–31) has two overloads:
- `Forward(predictions, targets)` — calls `Reduce(nll, Reduction, batchSize)`
- `Forward(predictions, targets, reduction)` — also calls `Reduce(nll, reduction, batchSize)`

Most loss classes have the same dual-overload pattern, but the 2-arg overloads
vary in whether they pass `Reduction` (the stored default) vs. the parameter.
The `divisor` parameter in `Reduce` is only used by `CrossEntropyLoss` (passes
`batchSize`); all other losses rely on the `?? elementwiseLoss.Length` fallback.
This subtle divergence could confuse maintainers extending the loss API.
