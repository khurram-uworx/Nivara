# NivaraIncident — Production Incident Replay and Investigation on a Columnar Engine

A reference application that models a production telemetry environment (services, requests, deployments, errors, latency, infrastructure signals, dependency relationships), replays a historical incident as if it were happening live, and investigates it through Nivara's typed, columnar, fused analytical pipeline — all in native .NET.

**Target audience:** engineers evaluating Nivara for production-grade analytical workloads, the Nivara team using this sample as a forcing function to discover missing capabilities and performance gaps.

## What it does

Given a deterministic telemetry snapshot (10M+ requests, 50+ endpoints, 10 regions, 100+ service instances, deployments), NivaraIncident reconstructs the incident timeline and answers questions like:

- Which service degraded first?
- Which deployment correlates with the degradation?
- Which endpoints contributed most to failures?
- How did latency evolve over time?
- Did retries propagate the incident? What was the blast radius?

It ships **reproducible incident scenarios** (no random failures) generated by a deterministic dataset generator:

| Incident | Story | Key analyses |
|----------|-------|--------------|
| **A — Database degradation** | PostgreSQL latency → orders → checkout → payment timeout → retry storm | which service degraded first, downstream propagation delay, retry amplification |
| **B — Bad deployment** | orders-api v4.21 deployed → exception rate ↑ → failures ↑ | deployment precedes degradation?, affected endpoints, time-to-customer-impact |
| **C — Traffic spike** | traffic ×8 → queue depth ↑ → latency ↑ → timeouts ↑ | which services saturated first, which recovered first |
| **D — Regional failure** | us-east/eu-west healthy, ap-south degraded | partitioning, grouping, ranking by region |

## Quick start

```bash
# Generate dataset for scenario A (10M+ records)
dotnet run --project samples/NivaraIncident.Cli -- generate --dataset ./data/incident-lab --scenario A --scale 1

# Run all five analyses
dotnet run --project samples/NivaraIncident.Cli -- analyze --dataset ./data/incident-lab --scenario A

# Benchmark (times each analysis)
dotnet run --project samples/NivaraIncident.Cli -- analyze --benchmark --dataset ./data/incident-lab --scenario A

# Benchmark all scenarios
dotnet run --project samples/NivaraIncident.Cli -- analyze --benchmark --dataset ./data/incident-lab --scenario all

# Streaming vs eager measurement
dotnet run --project samples/NivaraIncident.Cli -- bench-stream --dataset ./data/incident-lab --scenario A

# Kernel vectorization report
dotnet run --project samples/NivaraIncident.Cli -- bench-kernels --dataset ./data/incident-lab --scenario A

# Run analyses with chunked streaming output
dotnet run --project samples/NivaraIncident.Cli -- analyze --dataset ./data/incident-lab --scenario A --stream --chunk-size 50000

# Replay Parquet row groups with chunk-by-chunk progress
dotnet run --project samples/NivaraIncident.Cli -- replay --dataset ./data/incident-lab --scenario A --chunk-size 100000
```

## What it exercises

- **Typed expression execution** — `Filter`/`Select`/`Sort` via `ColumnExpressions.Col`/`Lit`, fused into kernel passes by the ADR-004 expression engine.
- **Rolling windows** — `RollingMean` for error-rate computation, `RollingMax` for queue-depth saturation tracking.
- **Shift / lead** — `Shift` for delta-since-previous-interval analyses (error-rate deltas).
- **Rank family** — `PercentRank` partitioned by region for regional incident analysis.
- **Typed LINQ GroupBy** — `NivaraQuery<T>.GroupBy().Select()` with `Count()`, `Sum()`, `Average()` for grouped aggregation.
- **Chunked / streaming execution** — `AsStream()` over Parquet row groups with `IAsyncEnumerable` and `IAsyncDisposable`.
- **Parquet / CSV ingestion** — `Parquet.ScanAsQueryFrame` and `Csv.ScanAsQueryFrame` for chunk-capable data sources.
- **Execution diagnostics** — `QueryFrame.GetExecutionDiagnostics()` for rows read, kernel counts, and elapsed time.
- **Benchmark harness** — `--benchmark` (per-analysis timing), `bench-stream` (streaming vs eager memory curve), `bench-kernels` (kernel vectorization rate via `DiagnosticsTracker`).

### Analysis pipeline

```
Parquet files (requests, deployments, instances, dependencies)
    │
    ▼
Ingestion.LoadParquet()  →  QueryFrame
    │
    ├── AnalyzeDegradationOrdering:   Filter → Sort → RollingMean → Shift → Select
    ├── AnalyzeDeploymentCorrelation: Filter → Sort → Select
    ├── AnalyzeSaturationOrdering:    Filter → Sort → RollingMax → Select
    ├── AnalyzeRegionalPartitioning:  Filter → Sort → PercentRank → Select
    └── AnalyzeGroupedAggregation:    Filter → Collect → manual group-by (or typed LINQ)
    │
    ▼
Results (NivaraFrame)  →  CLI output or streaming chunks
```

### Dataset generator

```
Seed = 42 (deterministic)
    │
    ├── Box-Muller transform for latency distribution
    ├── Dependency graph (gateway → orders → checkout → payments → ...)
    ├── Timeline injection: baseline → event → propagation → recovery
    │
    ▼
Output: requests.parquet, deployments.parquet, instances.parquet, dependencies.parquet
        + CSV equivalents
```

## Library gaps this example exposed

The Incident Lab is deliberately a **forcing function**: when the sample requires an awkward workaround, first ask whether Nivara itself is missing a capability, fix the core, then build on the fixed API.

| Gap | Problem | Resolution |
|-----|---------|------------|
| **`NivaraFrameExtensions.GroupBy` is a trap** | `GroupBy(frame, keys, aggregations)` validates columns, builds `GroupByOperation` **without aggregations**, and returns only the grouped keys — its own comment says "simplified implementation". | Used typed LINQ `frame.Query<T>().GroupBy().Select()` with `Count()`/`Sum()`/`Average()` for real aggregations, and manual dictionary aggregation after `Collect()` as a fallback. Gap confirmed in Phase 3a. |
| **No `&`/`&&` on `ColumnExpression`** | Cannot write `.Filter(A & B)` for compound predicates. | Chained `.Filter(A).Filter(B)` instead. |
| **No ternary on `ColumnExpression`** | Cannot write `cond ? litA : litB` in expression trees. | Computed derived columns after `Collect()` or used separate columns. |
| **Window-heavy queries defeat streaming** | `Rolling`, `Rank`, `Sort`, `GroupBy` are non-streamable — `AsStream` falls back to single-frame materialization. | Measured in Phase 4 bench-stream: chunk count == 1 for all chunk sizes on window-heavy queries. Filter-only prefix streams correctly (>1 chunks). See Limitations. |
| **Memory budget is advisory** | `StreamingBufferManager` exists but is not wired into the query path. | Measured in Phase 4 bench-stream: peak memory reflects full-frame materialization, not chunk-bounded streaming. |

## Performance: Nivara vs Polars

Apples-to-apples comparison of Nivara (C#) and Polars (Python) on the same Parquet data and the same analytical operations. Scenario A (database degradation).

### Running the benchmark

```bash
# 1. Generate a 1M-record dataset
dotnet run --project samples/NivaraIncident/NivaraIncident.Cli -c Release \
  -- generate --records 1000000 --dataset samples/data/benchmark-1m --scenario A

# 2. Nivara benchmark
dotnet run --project samples/NivaraIncident/NivaraIncident.Cli -c Release \
  -- analyze --benchmark --dataset samples/data/benchmark-1m --scenario A

# 3. Polars benchmark (same Parquet files)
cd samples/NivaraIncident/Python
pip install -r requirements.txt
python benchmark.py --dataset ../../../samples/data/benchmark-1m
```

### Results

| Analysis | Nivara (C#) | Polars (Python) | Ratio |
|----------|-------------|-----------------|-------|
| Degradation Ordering | 1788 ms | 40 ms | ~45× |
| Deployment Correlation | 1289 ms | 66 ms | ~20× |
| Saturation Ordering | 11 ms | 3 ms | ~3× |
| Regional Partitioning | 1170 ms | 20 ms | ~60× |
| Grouped Aggregation | 739 ms | 17 ms | ~44× |
| **Total** | **4997 ms** | **146 ms** | **~34×** |

*Recorded 2026-08-18 — Intel Core Ultra 7 255H, .NET 10.0.11, Polars 1.43.2, 1M records, scenario A.*

- Both sides read the **same Parquet files** generated by NivaraIncident.Cli.
- Each analysis is timed individually (Parquet scan + filter + computation + materialization).
- Nivara uses `Stopwatch`; Polars uses `time.perf_counter()`.
- Polars uses idiomatic operations (`rolling_mean`, `group_by`, `join_asof`) rather than porting Nivara's exact algorithm.
- No warmup passes — each analysis reads fresh from disk/cache.
- Optimizations applied since previous run: row-group predicate pushdown (#298), pre-captured column comparer for sort (#300), boxing elimination in Parquet reader (#297).

## Limitations

- **Web UI not yet implemented** — CLI only; ASP.NET Core dashboard planned for Milestone 2.
- **No Polars cross-validation tests yet** — analysis results are validated by structure/assertions, not fixture comparison.
- **`NivaraFrameExtensions.GroupBy` is unusable for aggregation** — returns keys only; typed LINQ or manual aggregation required.
- **Window-heavy streaming falls back to single-frame** — `AsStream` materializes the full frame when window operations are present. Measured in Phase 4: chunk count == 1 for all chunk sizes on Degradation Ordering (Sort + RollingMean + Shift + RollingMax). Filter-only queries stream correctly.
- **No learning rate scheduling or advanced query optimization** — straightforward execution, no adaptive strategies.
