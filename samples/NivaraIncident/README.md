# NivaraIncident — Production Incident Replay and Investigation on a Columnar Engine

A reference application that models a production telemetry environment (services, requests, deployments, errors, latency, infrastructure signals, dependency relationships), replays a historical incident as if it were happening live, and investigates it through Nivara's typed, columnar, fused analytical pipeline — all in native .NET.

**Target audience:** engineers evaluating Nivara for production-grade analytical workloads, the Nivara team using this sample as a forcing function to discover missing capabilities and performance gaps.

## What it does

Given a deterministic telemetry snapshot (10M+ requests, 50+ endpoints, 10 regions, 100+ service instances, deployments), NivaraIncident reconstructs the incident timeline and answers questions like:

- Which service degraded first?
- Which deployment correlates with the degradation?
- Which endpoints contributed most to failures?
- How did latency evolve over time?
- Did retries propagate the incident? What was the blast radius?

It ships **reproducible incident scenarios** (no random failures) generated by a deterministic dataset generator:

| Incident | Story | Key analyses |
|----------|-------|--------------|
| **A — Database degradation** | PostgreSQL latency → orders → checkout → payment timeout → retry storm | which service degraded first, downstream propagation delay, retry amplification |
| **B — Bad deployment** | orders-api v4.21 deployed → exception rate ↑ → failures ↑ | deployment precedes degradation?, affected endpoints, time-to-customer-impact |
| **C — Traffic spike** | traffic ×8 → queue depth ↑ → latency ↑ → timeouts ↑ | which services saturated first, which recovered first |
| **D — Regional failure** | us-east/eu-west healthy, ap-south degraded | partitioning, grouping, ranking by region |

## Quick start

```bash
# Generate dataset for scenario A (10M+ records)
dotnet run --project samples/NivaraIncident -- generate --dataset ./samples/data/incident-lab --scenario A --scale 1

# Run all six analyses
dotnet run --project samples/NivaraIncident -- analyze --dataset ./samples/data/incident-lab --scenario A

# Benchmark (times each analysis)
dotnet run --project samples/NivaraIncident -- analyze --benchmark --dataset ./samples/data/incident-lab --scenario A

# Benchmark all scenarios
dotnet run --project samples/NivaraIncident -- analyze --benchmark --dataset ./samples/data/incident-lab --scenario all

# Streaming vs eager measurement
dotnet run --project samples/NivaraIncident -- bench-stream --dataset ./samples/data/incident-lab --scenario A

# Kernel vectorization report
dotnet run --project samples/NivaraIncident -- bench-kernels --dataset ./samples/data/incident-lab --scenario A

# Grouped aggregation benchmark on Silk (CPU comparison via --benchmark)
dotnet run --project samples/NivaraIncident -c Release -- analyze --benchmark --silk --dataset ./samples/data/incident-lab --scenario A

# Analyze with Silk acceleration
dotnet run --project samples/NivaraIncident -c Release -- analyze --dataset ./samples/data/incident-lab --scenario A --silk

# Run Streamix scenarios with OpenBLAS (online AutoDiff path)
dotnet run --project samples/NivaraIncident -c Release -- streamix --dataset ./samples/data/incident-lab --scenario A --blas --threads 2

# Run analyses with chunked streaming output
dotnet run --project samples/NivaraIncident -- analyze --dataset ./samples/data/incident-lab --scenario A --stream --chunk-size 50000

# Replay Parquet row groups with chunk-by-chunk progress
dotnet run --project samples/NivaraIncident -- replay --dataset ./samples/data/incident-lab --scenario A --chunk-size 100000

# Run Streamix streaming scenarios (fault-tolerant, windowed analytics, online AutoDiff learning)
dotnet run --project samples/NivaraIncident -- streamix --dataset ./samples/data/incident-lab --scenario A
```

## What it exercises

- **Typed expression execution** — `Filter`/`Select`/`Sort` via `ColumnExpressions.Col`/`Lit`, fused into kernel passes by the ADR-004 expression engine.
- **Rolling windows** — `RollingMean` for error-rate computation, `RollingMax` for queue-depth saturation tracking.
- **Shift / lead** — `Shift` for delta-since-previous-interval analyses (error-rate deltas).
- **Rank family** — `PercentRank` partitioned by region for regional incident analysis.
- **Typed LINQ GroupBy** — `NivaraQuery<T>.GroupBy().Select()` with `Count()`, `Sum()`, `Average()` for grouped aggregation.
- **Chunked / streaming execution** — `AsStream()` over Parquet row groups with `IAsyncEnumerable` and `IAsyncDisposable`.
- **Parquet / CSV ingestion** — `NivaraParquetReader.ScanAsQueryFrame` and `Csv.ScanAsQueryFrame` for chunk-capable data sources.
- **Execution diagnostics** — `QueryFrame.GetExecutionDiagnostics()` for rows read, kernel counts, and elapsed time.
- **Benchmark harness** — `--benchmark` (per-analysis timing), `bench-stream` (streaming vs eager memory curve), `bench-kernels` (kernel vectorization rate via `DiagnosticsTracker`).
- **Streamix bridge** — `ToFlux`, `ToFluxWithTimestamp`, `ToFluxRows`, `BufferFrames` for event-driven streaming pipelines.
- **Online AutoDiff learning** — `GradientUtils.Grad()` + `Linear` + `Adam` + `MSELoss` over Streamix mini-batches for streaming ML training.

### Analysis pipeline

```
Parquet files (requests, deployments, instances, dependencies)
    │
    ▼
Ingestion.LoadParquet()  →  QueryFrame
    │
    ├── AnalyzeDegradationOrdering:   Filter → Sort → RollingMean → Shift → Select
    ├── AnalyzeDeploymentCorrelation: Filter → Sort → Select
    ├── AnalyzeSaturationOrdering:    Filter → Sort → RollingMax → Select
    ├── AnalyzeRegionalPartitioning:  Filter → Sort → PercentRank → Select
    ├── AnalyzeGroupedAggregation:    Filter → Collect → manual group-by (or typed LINQ)
    │
    ├── Streamix: Fault-tolerant streaming (ToFlux → Retry → Checkpoint → ForEachAsync)
    ├── Streamix: Event-time windowing  (ToFluxWithTimestamp → WindowByTime → FlatMap → per-window analytics)
    └── Streamix: Online AutoDiff       (ToFluxRows → BufferFrames → Grad → Linear → Adam)
    │
    ▼
Results (NivaraFrame)  →  CLI output or streaming chunks
```

### Streamix streaming scenarios

The `streamix` CLI command runs three scenarios demonstrating the Nivara × Streamix bridge:

| Scenario | Pattern | What it demonstrates |
|----------|---------|---------------------|
| **Fault-tolerant streaming** | `ToFlux` → `.Retry(3)` → `.Checkpoint()` → `.ForEachAsync()` | Resilience operators, chunk-level processing with automatic retry on failure |
| **Event-time windowed analytics** | `ToFluxWithTimestamp` → `.WindowByTime(5min, 1min)` → `.FlatMap(ToNivaraFrameAsync)` → per-window aggregation | Timestamp bridge, event-time windowing, collecting window items into NivaraFrames for columnar analytics |
| **Online AutoDiff learning** | `ToFluxRows` → `.BufferFrames(128)` → `Grad()` + `Linear` + `Adam` + `MSELoss` | Streaming ML training — bridge between Streamix event flow and Nivara AutoDiff |

These scenarios are implemented in `StreamixScenarios.cs` and can be run via:

```bash

```

## Library gaps this example exposed

The Incident Lab is deliberately a **forcing function**: when the sample requires an awkward workaround, first ask whether Nivara itself is missing a capability, fix the core, then build on the fixed API.

| Gap | Problem | Resolution |
|-----|---------|------------|
| **`NivaraFrameExtensions.GroupBy` simple overload is key-only** | `GroupBy(frame, keyColumns)` (no aggregations parameter) validates columns, builds `GroupByOperation` **without aggregations**, and returns only the grouped keys. The two-argument overload `GroupBy(frame, keys, aggregations)` works correctly. | Used typed LINQ `frame.Query<T>().GroupBy().Select()` with `Count()`/`Sum()`/`Average()` for real aggregations, and manual dictionary aggregation after `Collect()` as a fallback. |
| **No `&`/`&&` on `ColumnExpression`** | Cannot write `.Filter(A & B)` for compound predicates. | Chained `.Filter(A).Filter(B)` instead. |
| **No ternary on `ColumnExpression`** | Cannot write `cond ? litA : litB` in expression trees. | Computed derived columns after `Collect()` or used separate columns. |
| **Window-heavy queries defeat streaming** | `Rolling`, `Rank`, `Sort`, `GroupBy` are non-streamable — `AsStream` falls back to single-frame materialization. | Measured in Phase 4 bench-stream: chunk count == 1 for all chunk sizes on window-heavy queries. Filter-only prefix streams correctly (>1 chunks). See Limitations. Filed as [#307](https://github.com/khurram-uworx/Nivara/issues/307). |
| **Memory budget is advisory** | `StreamingBufferManager` exists but is not wired into the query path. | Measured in Phase 4 bench-stream: peak memory reflects full-frame materialization, not chunk-bounded streaming. Filed as [#308](https://github.com/khurram-uworx/Nivara/issues/308). |

## Silk (OpenCL) acceleration

`--silk` is opt-in and fail-loud: it runs the available Silk (OpenCL) kernels and exits
non-zero (with a `SilkRuntime` exception) when no OpenCL device is present. Other analyses
stay on CPU unless a kernel has been individually prototyped and shown profitable.

### Availability and status

Measured on the shared iGPU (`Intel(R) Graphics`), .NET 11, Release; rows are legacy single-pass
captures (convention not recorded in the original capture) unless noted. CPU = managed Nivara path,
Silk = OpenCL path.

| Kernel / capability | Wired into `--silk`? | Scale | CPU (ms) | Silk (ms) | Ratio (Silk/CPU) | Verdict | Notes |
|---|---:|---:|---:|---:|---:|---|---|
| `grouped_hash_reduce_partial` | Yes — Grouped Aggregation | 10k | 32.5 | 38.4 | 1.18x | slower | Wired at all scales; remains an opt-in experiment |
| `grouped_hash_reduce_partial` | Yes — Grouped Aggregation | 100k | 236.3 | 247.9 | 1.05x | slower | |
| `grouped_hash_reduce_partial` | Yes — Grouped Aggregation | 1M | 1533.2 | 1474.6 | 0.96x | ~4% faster | |
| `grouped_multistat_reduce_partial` | No (staged) | 100k | 0.28 | 1.19 | 4.258x | slower | Count/errors/sum/squares/min/max in one pass |
| `rolling_mean` | No (staged) | 100k | 0.47 | 7.75 | 16.426x | slower | Strided sliding-window mean |
| `rolling_max` | No (staged) | 100k | 0.65 | 6.00 | 9.268x | slower | Strided sliding-window max |
| `rolling_min` | No (staged) | 100k | 0.40 | 5.39 | 13.457x | slower | Strided sliding-window min |
| `percent_rank` | No (stays CPU) | — | — | — | — | n/a | Partition-local ordering required; no OpenCL sort primitive; see issue #1038 |

**Percent rank (issue #1038).** `AnalyzeRegionalPartitioning` uses `PercentRank` partitioned by
region, but it is deliberately **not** prototyped as a Silk kernel and stays on CPU. Unlike the
rolling kernels above, percent rank needs partition-local *ordering* (sort each partition by the
order keys, then `(rank - 1) / (partitionSize - 1)`), not a per-element pass; Silk has no sort
primitive, and a naive counted-ranking kernel is O(n²) per partition and would be slower than
the CPU `RankKernel` path. The sibling incident kernels are already slower than CPU on the
shared iGPU (rolling mean 16.4×, rolling max 9.3×, multi-stat 4.3×), so there is no evidence
a GPU percent rank would win; it would only be revisited with a discrete-GPU measurement
showing a clear speedup or a clean OpenCL sorting primitive. `RankKernel` remains the
reference and correctness baseline.

Policy: `--silk` is the user's choice. If requested, the wired kernel runs even when
CPU is faster. Slower kernels remain implemented and parity-tested for future reuse, but
are **not wired** because they do not clear Nivara's Phase 5 revisit bar (clear speedup
on the target hardware, plus a kernel-specific proof before integration).

### Silk profitability (experimental, not wired up)

`samples/Nivara.Samples/Incident/SilkProfitability.cs` (formerly `GpuProfitability`)
contains a pre-flight cost estimator for the grouped-aggregation Silk offload: 100k-row CPU
sample, extrapolated CPU cost, first-pass GPU cost model, offload only under 90% margin.

**Status:** not invoked by `--silk` or any current CLI path. It is retained for future
evaluation of an automatic/conditional offload mode; constants are first-pass placeholders
and must be recalibrated against measured Silk timings before use.

## BLAS (OpenBLAS) acceleration

`--blas` is opt-in and applies only to the `streamix` command's online AutoDiff path
(`Linear`/`Adam`), not the analytics pipeline. It registers the OpenBLAS GEMM/GEMV
provider process-wide for that run; the managed path remains the default and bit-identical
fallback. Requires `lib/libopenblas.dll` at the repo root.

### Availability and status

Parity with `NivaraInference` (`--blas`, `--threads`, `--blas-threads`, default 1).
Probe numbers (from `tests/Nivara.SimdProbe -- blas`, `managed/blas` ratio): 5 untimed warmups per leg,
then 20 interleaved A/B rounds alternating which leg is measured first, median (and min) ms,
correctness gate `maxAbs <= 1e-3`. Haswell-class, OpenBLAS 0.3.34, .NET 11, Release.

| Shape | M | K | N | managed (ms) | blas (ms) | ratio |
|---|---:|---:|---:|---:|---:|---:|
| square-256 | 256 | 256 | 256 | 12.76 | 0.69 | 18.56x |
| square-512 | 512 | 512 | 512 | 4.04 | 2.18 | 1.85x |
| tall-1024x64 | 1024 | 1024 | 64 | 2.89 | 1.03 | 2.81x |
| batched-8x768 | 8 | 768 | 768 | 1.09 | 1.78 | 0.61x |
| hidden-768 (GEMV) | - | 768 | 768 | 0.11 | 0.06 | 1.87x |
| hidden-4096 (GEMV) | - | 4096 | 4096 | 3.56 | 3.47 | 1.03x |
| vocab-768x30522 (GEMV) | - | 768 | 30522 | 8.27 | 6.36 | 1.30x |

BLAS wins on larger square/tall GEMM and most GEMV, but loses on small-batch
(`batched-8x768`: 0.61x) and is within noise on `hidden-4096` (1.03x). Online
learning here uses small batches (batch size 128), the regime where BLAS does not help,
so it stays opt-in.

Policy: `--blas` is the user's choice. If requested, the provider is registered even
when CPU is faster. The managed path remains the default.

## Performance: Nivara vs Polars

Apples-to-apples comparison of Nivara (C#) and Polars (Python) on the same Parquet data and the same analytical operations. Scenario A (database degradation).

### Running the benchmark

```bash
# 1. Generate a 1M-record dataset
dotnet run --project samples/NivaraIncident -c Release \
  -- generate --records 1000000 --dataset samples/data/benchmark-1m --scenario A

# 2. Nivara benchmark
dotnet run --project samples/NivaraIncident -c Release \
  -- analyze --benchmark --dataset samples/data/benchmark-1m --scenario A

# 3. Polars benchmark (same Parquet files)
cd samples/NivaraIncident/Python
pip install -r requirements.txt
python benchmark.py --dataset ../../../samples/data/benchmark-1m
```

| Analysis | Nivara (C#) | Polars (Python) | Ratio |
|----------|-------------|-----------------|-------|
| Degradation Ordering | 1061 ms | 38 ms | ~28× |
| Deployment Correlation | 1078 ms | 73 ms | ~15× |
| Saturation Ordering | 1 ms | 4 ms | ~0.3× |
| Regional Partitioning | 2113 ms | 48 ms | ~44× |
| Grouped Aggregation | 798 ms | 16 ms | ~50× |
| **Total** | **5051 ms** | **178 ms** | **~28×** |

*Recorded 2026-08-21 — Intel Core Ultra 7 255H, 16 logical processors, .NET 10.0.11, Polars 1.43.2, 1M records, scenario A.*

This table covers the five analyses that were benchmarked on that date. `analyze` now also runs a
sixth — the typed LINQ grouped aggregation — which is **not** in this table: `Python/benchmark.py`
has no Polars counterpart for it, so there is no measured comparison to report rather than an
unmeasured row.

- Both sides read the **same Parquet files** generated by NivaraIncident.
- Each analysis is timed individually (Parquet scan + filter + computation + materialization).
- Nivara uses `Stopwatch`; Polars uses `time.perf_counter()`.
- Polars uses idiomatic operations (`rolling_mean`, `group_by`, `join_asof`) rather than porting Nivara's exact algorithm.
- No warmup passes — each analysis reads fresh from disk/cache.

## Limitations
- **Boundary operations still materialize** — `Sort`, `GroupBy`, `Join`, `Distinct`, rank-family windows, and broadcast aggregates execute once over concatenated data, so the incident benchmark's Sort-before-window analyses yield a single chunk regardless of `--stream`. Visible via `ExecutionDiagnostics.StreamMaterializationCount`; see `docs/STREAMING.md`.
- **`NivaraFrameExtensions.GroupBy` simple overload is key-only** — the parameterless `GroupBy(frame, keyColumns)` returns grouped keys only; use the two-argument `GroupBy(frame, keys, aggregations)` overload or typed LINQ for real aggregations.
- **No learning rate scheduling or advanced query optimization** — straightforward execution, no adaptive strategies.
