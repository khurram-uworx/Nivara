# NivaraIncident — Production Incident Replay and Investigation on a Columnar Engine

A reference application that models a production telemetry environment (services, requests,
deployments, errors, latency, infrastructure signals, dependency relationships), replays a
historical incident as if it were happening live, and investigates it through Nivara's typed,
columnar, fused analytical pipeline — all in native .NET.

**Target audience:** engineers who want to see whether a serious production-grade analytical
application can be built on top of Nivara, and the Nivara team itself, which uses this sample as
a forcing function to discover missing capabilities and performance gaps.

> The objective is not to build another dashboard demo. It is to answer:
> *Could a serious .NET engineer build a production-grade analytical application on top of Nivara?*
> — and in the process make the library better.

## What it does

Given a deterministic telemetry snapshot (10M+ requests, 50+ endpoints, 10 regions, 100+ service
instances, logs, traces, deployments), NivaraIncident reconstructs the incident timeline and
answers questions like:

- Which service degraded first?
- Which deployment correlates with the degradation?
- Which endpoints contributed most to failures?
- How did latency evolve over time?
- Did retries propagate the incident? What was the blast radius?

It ships **reproducible incident scenarios** (no random failures) generated by a deterministic
dataset generator:

| Incident | Story | Key analyses |
|----------|-------|--------------|
| **A — Database degradation** | PostgreSQL latency → orders → checkout → payment timeout → retry storm | which service degraded first, downstream propagation delay, retry amplification |
| **B — Bad deployment** | orders-api v4.21 deployed → exception rate ↑ → failures ↑ | deployment precedes degradation?, affected endpoints, time-to-customer-impact |
| **C — Traffic spike** | traffic ×8 → queue depth ↑ → latency ↑ → timeouts ↑ | which services saturated first, which recovered first |
| **D — Regional failure** | us-east/eu-west healthy, ap-south degraded | partitioning, grouping, ranking by region |

Three surfaces are planned:

1. **CLI** — `dotnet run -- incident analyze ./data/incident-421` for engineers and benchmarks,
   printing top impacted services, correlated events, and execution diagnostics.
2. **Web UI** — ASP.NET Core dashboard (timeline, services, endpoints, regions, dependencies,
   errors, deployments, query plan). Every important number shown is calculated by Nivara.
3. **Library API** — the underlying analyses stay visible as normal Nivara query code so the
   sample teaches the API rather than hiding it.

The killer demo is **Incident Replay**: historical Parquet analysis and live/replay analysis
converge on the same Nivara pipeline (`IAsyncEnumerable<Chunk>` → Nivara plan → fused operators →
bounded buffers → CollectAsync).

## Nivara capabilities exercised

The IDEA deliberately avoids hiding the library behind LINQ-to-objects. The sample is written to
exercise, in cooperation, one real-world workload:

- **Typed expression execution** — `Where`/`Select` over typed `r["Column"]` expressions,
  fused into a single kernel pass (ADR-004 fused expression engine).
- **Computed ordering** — sort by a calculated score instead of a raw column.
- **Rolling / cumulative windows** — service-health error-rate views with `minPeriods` gating and
  explicit null semantics.
- **Shift / lead** — "delta since previous interval" analyses (error-rate deltas, latency deltas).
- **Rank family** — `RowNumber`, `Rank`, `DenseRank`, `PercentRank`, partitioned and ordered,
  cross-validated against Polars.
- **Partitioning** — GroupBy + per-group windows and ranks; regional incident D leans on this.
- **Percentiles / distributions** — incident analysis requires latency percentiles (P50/P95/P99)
  and median; this is a **known missing capability** (see Gaps below).
- **Chunked / streaming execution** — `AsStream()` over Parquet row groups with bounded-channel
  backpressure and end-to-end cancellation.
- **Execution diagnostics & query-plan visibility** — the UI exposes the logical plan, physical
  kernel chain, and per-run diagnostics (rows, kernels, peak memory, elapsed).

incorrect abstraction, fix the core, then build the sample on the fixed API.

(by prior roadmap work or earlier samples), or open (to be fixed while implementing this sample).

### Open gaps to fix while implementing this sample

These are the items the implementation plan (`../Incident-PLAN.md`) targets. Gaps 1, 2, 3, 4, and
7 above were fixed in core by the Phase 1 branch; the remaining items below are **deferred** to a
follow-up tracked in issue #284 (Phase 2 AutoDiff cleanup/SIMD = gaps 9/10; Phase 3 sample
measurements = gaps 5/6/8), except gap 8's design-test which is escalated to Phase 3. Each was
verified as genuinely missing on `main` by the pre-implementation audit.

#### 5. Window semantics across chunk boundaries (non-streamable fallback) — **DEFERRED to issue #284 (Phase 3 measurement)**

The IDEA's flagged gap #1 stands: window expressions (`ColumnExpressions.RowNumber/.Rank/...`),

The IDEA's flagged gap #1 stands: window expressions (`ColumnExpressions.RowNumber/.Rank/...`),
`Rolling`, `Cumulative`, `Shift`, `Rank`, `Sort`, `GroupBy`, `Join`, `Distinct` are
**non-streamable** (`StreamingExecutionStrategy.NonStreamableOperations`, `:10`). `AsStream` is
all-or-nothing (any boundary op → single merged frame, `docs/STREAMING.md:36-55`); `CollectAsync`
uses flush-concatenate-resume. The sample should **measure** whether window-heavy replay queries
defeat true streaming, and decide (with evidence) whether cross-chunk window computation is a
core improvement worth pursuing.

#### 6. Memory budget is advisory, not a hard limit — **DEFERRED to issue #284 (Phase 3 measurement)**

The bounded `Channel<T>` (capacity clamped to [2,16], `StreamingExecutionStrategy:86`) bounds
in-flight chunks, but there is no byte-level enforcement on the query path. `StreamingBufferManager`
(`src/Nivara.Extensions/IO/StreamingBufferManager.cs:21`) exists but is deliberately **not wired
into** the query strategy (its only caller is the stub `ReadParquetStreamingInternal`). The sample
should stress this with a large replay and report peak memory vs budget.

#### 8. Query API ergonomics for group→aggregate→rank→filter — **DEFERRED to issue #284 (Phase 3 design-test)**

`QueryFrame` has `GroupBy` but no `Aggregate`/`Having`/`Where` alias (`Filter` is the only
predicate, `QueryFrame.cs:108`). The eager `NivaraFrameExtensions.GroupBy(frame, string[],
Dictionary<string, AggregationFunction>)` overload (`NivaraFrameExtensions.cs:1123-1156`) is a
trap: it validates columns, builds `GroupByOperation` **without aggregations**, and returns only
the keys — its own comment calls it a "simplified implementation". The typed
`NivaraGroupedQuery<TKey,T>` (`NivaraQuery.cs:300`) and `GroupByOperation` +
`GroupedAggregation` do support real aggregations, so group→aggregate is expressible, but the
plan-representability of "group → aggregate → rank → filter" should be exercised and reported
(the IDEA's design-test principle) before deciding whether the core needs a cleaner fluent path.

#### 9. ADR-001 residual cleanup (dead branches inside the non-null domain) — **DEFERRED to issue #284 (Phase 2)**

The AutoDiff audit confirms the domain is **fully compliant** — no null-mask propagation remains
in hot paths; all 8 data-null checks are legitimate boundary enforcement. Two cosmetic dead
branches remain and should be removed while touching these files:
- `Gather` (`ReverseGradOperations.cs:2423-2441`): `TryGetSpan` fast path with an `else`
  indexer fallback that is unreachable post-boundary (ADR-001 consequence: `TryGetSpan` always
  succeeds in-domain).
- `BroadcastGradient` (`GradOperationKernels.cs:241-258`): same `TryGetSpan` + `ArrayPool`
  fallback pattern.

#### 10. SIMD opportunities discovered by the audit — **DEFERRED to issue #284 (Phase 2)**

These are performance improvements, not correctness fixes. Prioritized:

| Location | Loop | Opportunity |
|----------|------|-------------|
| `ReverseGradOperations.Pow` (`:1637-1655`) | scalar `Math.Pow` | **Route through existing SIMD `GradOperationKernels.ApplyPow`/`ApplyPowGradient`** (already `TensorPrimitives.Pow`) — the reverse op is the inconsistent outlier vs forward-mode |
| `Adam.cs:125-139` / `AdamW.cs:111-125` | generic scalar fallback | Reached only for types other than float/double/Half; under `IFloatingPointIeee754<T>` all three dispatch to dedicated SIMD kernels (float `:83`, **double `:99`/`:85`**, Half `:111`/`:97`) — the tail loop is effectively defensive, not a live `double` gap |
| `GradOperationKernels.cs:226-227` | RMSNorm grad `g*invRms - x*scale` | `TensorPrimitives` multiply/subtract chain |
| `ReverseGradOperations.cs:2651-2683, 2723-2749` (+ `ForwardGradOperations.cs:1357-1454`) | `BroadcastMultiply`/`BroadcastAdd` channel-strided loops | Per-channel-run `TensorPrimitives` when contiguous |
| `SGD.cs:20-39` | momentum step loop | `TensorPrimitives.MultiplyAdd` chain |

The `Pow` SIMD inconsistency (item 1) is a small, high-value, low-risk win that should land with
a PyTorch-parity regression test (the NivaraTorch fixture suite covers Pow).

## Performance goals

The IDEA's illustrative targets, to be validated by the sample's diagnostics view:

```text
Dataset       4.2 GB        Rows 48.9M (streamed in 3 chunks)
Elapsed       2.14 s        Peak memory 412 MB (bounded channel in flight)
Kernels       5 executed    0 per-row boxing
```

The important properties are **bounded memory** during replay (channel backpressure) and
**visible kernel selection** (fused / SIMD vs scalar) in the diagnostics view.

## Limitations

- **Not yet implemented** — this README documents the audited gap inventory and the planned
  surface; the implementation plan lives in `../Incident-PLAN.md`. All "planned surface" items
  above are targets, not delivered code. Phase 1 core gap-fills (gaps 1, 2, 3, 4, 7) are resolved
  on `khurram/incident`; the sample itself is still to be built (Phase 3, issue #284).
- `AsStream` window-heavy queries fall back to single-frame materialization (Gap 5) — the replay
  demo may not be truly chunked for window-heavy analyses until this is measured and addressed.
