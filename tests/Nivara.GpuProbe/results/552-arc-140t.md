# GpuProbe — Arc 140T same-host eight-leg profile (#552)

Same-host repeated profile of the eight GpuProbe legs for `dot16`, `silu` and
`gemv`, measured on **this** host per issue #552. It is the **Arc 140T half** of the
correction that #553 (Iris Xe) carries the other half of. The `README.md` decision
table, `docs/ILGPU.md`, `docs/ACCELERATION.md` and the per-leg case-study docs are
**not** edited from this file alone — those corrections land jointly, once both hosts
are measured, with the two readings side by side (tracked in #599).

## Method

- **One `kernels` invocation**, Release build (`net11.0`), all legs in-process.
- Each leg runs its own steady state (1 warmup + best-of-25 synchronized dispatches)
  as before; the whole leg set is then swept **5 times** with a **rotating leg order**
  so no leg is systematically first or last.
- Per cell this file reports the **median and the min–max band** across the 5 sweeps,
  not a single sample. `n=5` for every measured cell.
- Correctness is gated once (round 0) against the production Nivara CPU kernels with
  `|leg − cpu| ≤ 1e-6 + 1e-5·|cpu|`; every runnable leg's `dot16` and `gemv` pass (see
  below), and `silu` passes on every leg except OV bf16.
- The process **exit code was captured** (`405`) and is appended to the raw log as
  `=== process exit code: 405 ===` — it is the harness's own return value, not a
  pipeline's. **Pre-#606 record:** this exit predates the diagnosed-honest gate
  (issue #606). Under that gate the same hardware exits **3** = 3 SYCL-unavailable
  + **0** unexpected — the 402 OV-bf16 silu failures are re-classified as
  diagnosed-honest (each ≤ 2 half-ULP from the F16 mirror, see
  [OPENVINO.md](../OPENVINO.md) §3); the raw log below is left verbatim as the
  pre-change measurement.
- Raw harness stdout: [`552-arc-140t.raw.txt`](552-arc-140t.raw.txt).

## What this host's bands say (scoped to Arc 140T)

- **`gemv`**: **Silk.NET (100.6 µs) is the fastest GPU row by median, and it is disjointly
  faster than every other runnable leg except OV bf16**, whose much wider band
  `[92.8–201.0]` reaches down over Silk.NET's `[90.3–103.7]`. By the rule these issues set
  — overlapping bands are a tie — the two are therefore a **tie at the front on this
  host**, and that tie is this host's answer to the README's "which leg wins the GEMV"
  question. It is not stated here as a kernel property until it survives the Iris Xe
  comparison in #599.
- **`gemv`, the rest**: OV f32 `[147.9–183.0]`, ILGPU `[135.8–167.4]` and ComputeSharp
  `[136.7–174.5]` **pairwise overlap** and form one tied band. DX12 `[178.6–342.4]` is
  disjointly slower than Silk.NET, ILGPU and ComputeSharp, but its band overlaps OV f32
  and OV bf16, so its position against the middle group is not fully readable either.
- **`silu` and `dot16`**: **Silk.NET and ILGPU are a tie** (bands overlap:
  6.2–15.3 vs 7.0–18.1 on `silu`; 6.5–16.4 vs 8.7–17.4 on `dot16`). ComputeSharp is
  disjointly slower than both on `silu` and slower than Silk.NET on `dot16`; DX12 is the
  slowest runnable leg on both small kernels (launch-bound at 576 elements).
- **CPU**: on `dot16` the CPU leg's band **overlaps Silk.NET's and ILGPU's**, so "CPU wins
  `dot16`" is **not** readable as an ordering here — a tie is reported as a tie. `silu` is
  ~4× CPU for the fastest GPU legs (Silk.NET 6.7 vs CPU 28.1; ILGPU 8.6), **not** the 5–14×
  the current README states. `gemv` is a clear GPU win at ~23× (Silk.NET 100.6 vs CPU
  2348.9).

## Device-dependence vs the Iris Xe (for the joint correction)

Compared with [`553-iris-xe.md`](553-iris-xe.md) (same harness, same 5-sweep protocol,
same fixtures). Every pair of shared legs is compared on both hosts by whether its
min–max bands are **disjoint**; an overlap is a tie, per the rule these issues set. This
is a reading aid for #599, which owns the doc wording.

- **Magnitude**: the Arc is ~4–6× faster on `gemv` across every shared leg — Silk.NET
  100.6 vs 486.2, ILGPU 144.2 vs 859.7, ComputeSharp 157.5 vs 574.0, DX12 250.4 vs
  705.8. The Arc is the newer, larger part (128 EU Xe2 vs 96 EU Tiger Lake), so the
  direction is expected; the ordering is the open question.
- **Holds on both hosts** (a tie on both, or disjoint in the same direction on each):
  - `gemv`: `Silk.NET < ILGPU`, `Silk.NET < DX12`, `ComputeSharp < DX12`, and DX12,
    Silk.NET and ComputeSharp all `< CPU`.
  - `dot16`: **Silk.NET ≈ ILGPU (tie)**; Silk.NET `< ComputeSharp` and ILGPU
    `< ComputeSharp`; Silk.NET `< DX12` and ILGPU `< DX12`; `CPU < ComputeSharp` and
    `CPU < DX12`.
  - `silu`: **Silk.NET ≈ ILGPU (tie)** and **CPU ≈ ILGPU (tie)**; Silk.NET
    `< ComputeSharp` and ILGPU `< ComputeSharp`; Silk.NET `< DX12` and ILGPU `< DX12`.
  - So on the small kernels **ComputeSharp is disjointly slower than Silk.NET and ILGPU
    on both hosts** — that carries as stated. DX12's own rank is the host-dependent one
    (DX12 vs ComputeSharp is a tie on the Iris Xe and a ComputeSharp win on the Arc).
- **A strict flip — device-dependent**: `gemv` **ILGPU vs DX12**. Iris Xe: DX12 (705.8)
  `<` ILGPU (859.7), disjoint. Arc: ILGPU (144.2) `<` DX12 (250.4), disjoint. The same
  pair reverses between the two devices and must not be stated as a kernel property.
- **An ordering on one host only — not general** (disjoint on one host, a tie on the
  other): `dot16` CPU vs Silk.NET and vs ILGPU; `dot16` ComputeSharp vs DX12; `silu` CPU
  vs DX12, vs ComputeSharp and vs Silk.NET (`Silk.NET < CPU` holds only on the Arc);
  `gemv` CPU vs ILGPU; `gemv` ILGPU vs ComputeSharp; `gemv` Silk.NET vs ComputeSharp.
  None of these is readable off one host's table.
- **A correction the joint pass must not inherit**: `553-iris-xe.md` states the Iris Xe
  `gemv` ordering (`Silk.NET < ComputeSharp < DX12 < ILGPU`) with "the bands are
  disjoint". That holds for every pair **except Silk.NET vs ComputeSharp**, whose bands
  `[469.4–583.9]` and `[536.3–628.2]` overlap — so on the Iris Xe that pair is a **tie**
  by the same rule, making `Silk.NET < ComputeSharp` host-dependent rather than a
  property. Filed as #607.
- **OpenVINO is Arc-only.** The Iris Xe cannot run either OV leg (no `openvino_c.dll`),
  so every OV figure must stay labelled as this host's. This host's OV bf16 `gemv` band
  is `[92.8–201.0]` — the README's series figure `137.9` sits **inside** it, and the
  earlier same-session `86.8–93.4` readings sit at or just **below** its lower edge.
  That is consistent with them being single-sample draws from the same distribution,
  which is precisely why the ordering in [SILK.md](../SILK.md) was reported from a
  same-session A/B. On this host today the two are a **tie**.
